## 卡牌目录页的「信息登记」标红

「卡牌目录」页会拉一次 `GET /v1/api/card-marks/codes`（全部登记记录），叠加显示：

- **一级**：卡包卡片上多一枚 `登记 N` 角标，N = 前缀等于该包编号的登记**条数**（一个编号两档就算 2 条）
- **二级**：被登记的卡，表格行 / 卡片瓦片底色变纯红（与上传页 `.card-uncollected` 同一个色值）
- 编号旁边的小圆点区分两种命中：**红点** = 编号一字不差；**橙点** = 靠去掉数字段的前导零才对上
  （登记写 `DL1-001`、目录里是 `DL1-01`）。橙点本身就是「这个编号位数要订正」的提示。
- 前缀不属于任何卡包的登记，一级底部单独列入口，**不会被静默丢掉**

### 粒度是 (编号, 罕贵度)

一条登记记的是 **`(编号, 罕贵度)` 这一对**，不是光一个编号：标了 `DL1-045·N`，
目录里 `DL1-045` 的 `N` 变红，同编号的 `NPR` 不受影响。

- **罕贵度留空 = 不限罕贵度**（通配）。存量那批迁移过来的记录都是空的，行为跟以前完全一样 ——
  **整个编号**变红，不挑罕贵度。所以「编号错」这种整体性问题仍然只需登记一条。
- 比对口径 = **去空格 + 转大写**，其余一字不差。**不做**去掉 `(N)` 后缀那类归一化 ——
  实测库里 `cards` / `cardcatalogs` / `listedcards` 三张表的罕贵度**零条带后缀**，用不上。
- 上传页登记时卡片罕贵度为空 → 记成通配那条；有值 → 记成对应那一档。
- 后台清单页（`card-marks-pack` / `card-marks`）的罕贵度列**可以直接改**，改的是「这条管哪一档」。

一级底部会把卡包前缀对得上、但**对不上的原因**分开列出来：

- `DL1-045（本包没有这个编号）` —— 编号在卡表里压根没有
- `DL1-045·N（本包没有这个罕贵度）` —— 编号有、只是没印这一档，这才是用户要的「精准错误点」

> 这套判据是实测定的：94 条登记里只按字面精确匹配只能对上 2 条，加上去前导零的归一化能对上 50 条，
> 且 31969 条目录行里**零冲突**（没有两条目录会被同一个归一化键撞上）。
>
> 罕贵度那一层同样是实测的：上传页写标读的是 `cards.rarity`、目录页读标读的是 `cardcatalogs.rarity`，
> 8567 对 `(编号, 罕贵度)` 里只有 3 对对不上（`DL1-001(N)`、`DL1-010(N)`、`DL2-17(N)`），
> 而且正是手上那批手工订正中的坏数据 —— 所以**没有引入新的「标了不红」**。

## 卡牌目录页的「卡包清单」一次拉全（V1.2.54）

第一层那网格里列的是**全部卡包**，接口 `GET /packs` 是**按页**给的（`page` / `perPage`，
每页上限 2000）。以前页面写死只拉第一页，于是「包数一旦超过 2000」就会**静默少显示** ——
接口只回前 2000 条，页面也从不看 `total`，看着像那些包不存在。

现在 `fetchPacks` 顺着响应里的 `totalPages` 一页一页拉，拉满为止。几个取舍记在这：

- **没有做成「上一页 / 下一页」的翻页 UI**。本页的搜索、分类、状态三个筛选都是拿 `packs`
  这一份**全量**在本地筛的（`filteredPacks`）。真分页之后筛选只会作用在当前这一页上 ——
  搜「QCAC」而它在第二页，第一页搜出来就是空的，看着像没这个包。要做真分页，得把三个筛选
  一起搬到服务端，那是另一件事。
- **也不是把 `perPage` 调大**。那只是把「931 个包刚好没超」换成「2000 个刚好没超」，
  过线那天照样静默少显示。循环拉才是真的没有上限。
- 循环里带了 `page <= 50` 的兜底，防止万一 `totalPages` 报得离谱时转成死循环
  （50 × 2000 = 10 万个包，够用；真到那天再说）。
- 拉完会重算 `buildPackMarkCounts()`（包的集合刚变，登记归属得跟着重算）。

## 卡牌目录页的「改卡牌编号」

编辑弹窗里的「卡牌编号」现在**可以改**了（以前是只读的）。改一个编号会同时动四处：

| 动什么 | 怎么动 |
|---|---|
| 图源图片文件名 | `旧编号-*.jpg` → `新编号-*.jpg`，`-异画号` 那段原样保留 |
| `{包名}.json` | 把里面的 `code` 一起改掉 |
| `cardcatalogs` | 那一行的 `code` |
| `cards` | 库存里用到这个编号的卡（所有库合计） |
| `cardmarks` | 这个编号的「信息登记」**会被删掉** —— 编号修好了，标记就该消失 |

**五道保险**（改编号是整个系统里唯一不可逆的操作，所以做得格外啰嗦）：

1. 点「确认更改」先发一次只读的 `dryRun`，把影响面摊开再问一次：
   重命名几个文件、几行目录、几张库存卡、登记会不会被删、备份落在哪。
2. 前置校验不过直接在第一次就拒掉，**一个文件都不动**：
   新编号形状不对 / 新编号在目录里已存在（撞唯一索引）/ 图源里没有这个包目录。
3. 改名之前，受影响的图片**先复制**一份到 `Server\Storage\rename-backup\{时间戳}\`，能捞回来。
4. 全程写审计 `Server\Storage\rename-audit\{时间戳}-{旧}-{新}.json`，
   含被删掉的那条登记记录原文，可人工恢复。
5. 执行顺序是**磁盘 → 目录 → 库存卡 → 登记**，任何一步失败就按逆序补偿回滚；
   MongoDB 是单机（没有多文档事务），只能靠这个。

> 这条链路有两个**只有页面层测试能发现**的坑，记在这里免得再踩：
> - 弹窗认行靠 `_rowKey` 而不是编号 —— 编号本身会变，用它当键的话改完编号整行的 DOM 都会被重建。
>   `_rowKey` 只存在前端内存里，写包 JSON 时有 `stripInternal()` 把 `_` 开头的字段剔掉。
> - 改编号后**要看浏览器里的真实表现**。`renameVisible` 这类漏声明的变量不会报错，
>   只会变成 `ReferenceError` 被 `catch` 吞成「盘点失败，网络或服务异常」——
>   服务端日志干干净净，接口测试也全绿，只有点开页面才看得见。

## 卡牌目录页的「卡牌详情」：点一下就存

V1.2.50 起，弹窗里的「确认更改」**就是保存**，顶栏那对 ✏️ 修改 / 💾 保存已经去掉。

以前不是这样：「确认更改」只把值塞进内存里的暂存副本 `edits`，再顺手打开「修改模式」，
真正写库要另点顶栏的 💾 保存 —— 也就是说**「确认更改」是个假确认**，看着像存好了，其实一个字
都没进库；再叠上这个页面**没有任何离开守卫**（`goBack` 直接返回），改了不点保存就静默丢改动。
现在整页只剩一条路径：**点开一张卡 → 改 → 确认更改 → 立刻落库**，没有「未保存」这种状态，
丢改动的坑自然也就不存在了。

三个按钮的去向：

| 原来 | 现在 |
|---|---|
| 顶栏 ✏️ 修改 / 💾 保存 | 去掉。`editMode` 整个概念作废，表格恢复成**纯只读** |
| 表格表头的「＋ 添加一行」 | 改成 `detail-btns` 里的「＋ 新增一张卡」。**不能放在表格上方**：`.card-table-wrap` 在 <900px 是 `display:none`，手机上根本够不着 |
| 表格里每行的 🗑 | 搬进弹窗底部（`v-if="editRowKey"`，新增态下没有这张卡可删）。同样是因为那张表手机上不显示 |

「改卡牌编号」那套 dryRun + 二次确认**保留不动** —— 编号不是普通字段，它同时出现在图源文件名、
目录、包 JSON、库存卡四个地方。弹窗里如果既改了编号又改了别的字段，编号那条确认走完，
剩下的字段会**接着自动落库**，不用再点第二遍。

后端 `PUT /packs/:code` 顺手补了三个窟窿（都是「单行提交」这条新路径才暴露出来的）：

1. **只删不增时磁盘包 JSON 更新不到。** `writePackJson` 是**只更新、从不删除**的（import-pack /
   Excel 那条路靠它：传进来的是整份，没提到的编号不该被抹掉）。但 `cards: []` + `deleted: [一行]`
   时归并循环一次都不跑 → 库里那行没了、`totalCards` 也减了，`{包名}.json` 里**那一条原样留着**。
   现在调用方把「一行都不剩的编号」算好放进 `opts.removeCodes` 显式摘掉。
   注意摘除要在归并**之后**做，而且得用 `filter` 重建数组 —— `pos` 只记每个编号最后一次出现的下标。
2. **回读没带 `packCode`。** 同编号可能出现在别的包的行里，不过滤会把别包的罕贵度拼进本包的
   「、」串，还会让本包该摘的条目摘不掉。
3. **少了两句收尾。** `cardReview.bumpReviewVersion()`（`services/cardReview.js` 顶上写着
   「任何写 `cardcatalogs` 的路径之后都必须调」，而 PUT 一次都没引过）和 `invalidateTcgCaches(packCode)`
   （`writePackJson` 只刷了 `_indexCache`，未收录清单那几份还是旧的）。

几条口径：

- **删单张卡也会被库存拦。** 跟「删卡包」同一个口径（用户定的：直接禁止，先清库存）：
  `cards` 里还有这个编号的实物卡就不删，原因进 `errors[]`，库里一行不动。
- **服务端「静默跳过」的行照样回 `ok: true`。** 缺编号、卡密不是纯数字（`buildCatalogDoc` 直接
  `continue`）时 `saved` 是 0 而 `ok` 是 true —— 前端必须看 `saved` 而不是 `ok`，否则页面上会多出
  一行刷新就没的幽灵卡。`errors` 里还混着「包 JSON 回写失败（数据库已保存）」，那种库是对的，
  只看 `errors` 非空会误报成失败。
- **不做乐观锁。** 本机单用户后台，单行 PUT 只影响该三元组，不同行不会互相覆盖；同一行并发编辑
  是 last-write-wins。`{包名}.json` 只是镜像产物，Mongo 才是真值，刷新即自愈。
- **`has_data` 恒为 `true`**，哪怕包被删空。写成 `false` 的话 `openPack` 会直接拦下
  「⏳ 该卡包数据待爬取」，用户**再也进不去这个包**，也就用不了「＋ 新增一张卡」。

## 卡牌目录页的「卡牌详情」：卡密是三个卡名的钥匙（V1.2.57）

用户的原话：

> 我这个卡密在卡牌详细这边，我输入什么，上面的卡牌的相关的中文英文日文名称这三个名称也会随之
> 进行改变，但是跟他的那个卡图和他的编号没有关系，因为它是作为钥匙去找它的那个几个名称的

现在就是这个行为：在弹窗的**卡密**那一格敲字，右上方那三个只读卡名**停手 300ms 后**去
唯一目录里按这把钥匙取一次名字换掉。**编号栏和图源文件名一个字都不动** —— 卡密只是
「去哪儿取名字」的钥匙，不是这一行的身份。

| 敲进去的卡密 | 三格显示 |
|---|---|
| 唯一目录里有这条身份 | 那条身份的日文名 / 中文名 / 英文名 |
| 唯一目录里**没有** | 三格一律「—」（用户定的口径，见下） |
| 清空 | 退回按**编号**取（编号也是钥匙，只是优先级更低） |

### 为什么不能直接用现成的 `回填` / `查一条`

这是这个功能唯一的坑，也是它以前没做出来的原因。`services/cardNames.js` 的 `查一条`
（目录那几千行的卡名全靠它）在**卡密非空但查不到时会回退到编号**：

```js
const 卡密 = String(doc.extCode || '').trim();
if (卡密) { const h = 缓存.按卡密.get(卡密); if (h) return h; }
const 编号 = String(doc.code || '').trim();
return 编号 ? 缓存.按编号.get(编号) || null : null;   // ← 回退
```

目录行上这个回退是**对的**（几千行里有一大堆卡密报废、只有编号能对上，正是靠它才有名字）。
但拿它做实时预览就会假绿：用户在卡密格敲一个查不到的卡密，三格**原封不动**挂着这一行旧编号的名字，
看着像"查到了"，其实钥匙是废的 —— 用户会再说一次「改了名字没跟着变」。

所以新增了一条**严格版** `按输入取(卡密, 编号)`：卡密非空时**只**查卡密，查不到就 `null`，
**绝不回退到编号**。目录页弹窗走它，目录行的 `回填` 仍旧走带回退的 `查一条`，两条路各管各的。

新的只读路由 `GET /api/tcg/card-names?ext_code=&code=` 就是这条严格版的口子
（不加鉴权，跟本文件其他只读路由一致）。编号在路由里统一 `toUpperCase()` —— `carduniques`
里编号身份的键都是大写写进去的，`查一条` 不做归一，漏了这一步小写编号会白显示「—」。

### 顺手修掉的一个真 bug：`saveRow` 不再回传三个卡名

以前 `saveRow` 把行上的旧名字原样回传给 `PUT /packs/:code`（注释写着「只是为了让服务端
`卡名.收下()` 有个值可收」）。改卡密时钥匙已经换成了**新卡密**，`收下` 就拿着新卡密当身份、
把**旧卡的名字**写了进去，`$setOnInsert` 顺手造出一条本不存在的 `carduniques` ——
实测 `1000020 → 強欲の壺`，条数 13,883 → 13,884。

名字是「按钥匙现查出来的派生值」，这一行没有自己的名字可写，所以现在**根本不传**。
三个名字全空时 `收下` 一行都写不动（`补` 与 `现` 全等 → `continue` → `ops` 为空 → 不 `bulkWrite`），
所以不回传 = 零写入。`收下` 只在 `import-pack` / `POST /import` / Excel 导入这三条
**文件里真带名字**的路径上还有用，那三条一个字没动。

⚠️ **上一次实验造出来的那条 `1000020 → 強欲の壺` 还在库里**（清理被明确拒绝过）。
所以你现在在卡密格敲 `1000020`，三格仍会显示「強欲の壺」—— 那不是功能没生效，
是那个卡密在唯一目录里**真的已经有一条**了。想去掉请去「卡牌唯一目录」页删那一行。

### 另外两个跟着来的小改动

- **保存后定点刷这一行的三个名字。** 行上缓存的卡名会过期，而 `afterRowSaved` 的就地更新
  从来不碰 `jp_name/cn_name/en_name` —— 不刷的话改完卡密，**底下的表格行和卡片格**会一直挂着
  上一把钥匙的名字。不整包重拉（那要重取上千行、重算瓦片），就复用上面那条新路由补这三个字符串。
  **无条件刷**，不去比「身份变没变」：改编号那条路里 `doRenameCode` 在调 `saveRow` **之前**
  就把行上的 `code` 换成新编号了，比不出来。
- **`doRenameCode` 里补一刀。** 只改了编号、其余字段没动时 `saveRow` 根本不会被调用，
  上面那把刷新落不到。那种情况（卡密为空、编号才是钥匙）名字会过期，所以在那里把受影响的行
  收进一个数组直接刷一遍。

### 一处刻意的不一致

行上的名字是服务端 `回填` 出来的（卡密查不到会**回退到编号**），所以一个卡密报废、编号还有资料的卡，
弹窗**刚打开时**显示的是编号那组名字；用户一旦动了钥匙，就按严格版走、可能变成「—」。
这是故意的 —— 打开弹窗不该看到名字凭空消失，而"敲了钥匙"才是用户表达「我要按这把钥匙看」的动作。

## 卡牌详情弹窗里点图放大

V1.2.51 起，弹窗左上角那张卡图**点一下就全屏放大**。
框本身只有 132×184（手机 104×145），卡面上的小字、版本标、防伪标正对着屏幕也看不清。

图上**不带任何角标** —— V1.2.51 初版在右下角挂了「🔍 放大」，V1.2.52 按用户要求去掉了：
「那个放大的图标不要了…就是我点击图片可以直接放大就可以了」。框本身就是可点区域，
`cursor:pointer` 是唯一剩下的可点暗示（没图时连它也不给）。

走 `uni.previewImage` —— uni 自带的全屏看图，能缩放，跟「卡牌唯一目录」页里
「点缩略图看大图」是同一个写法，不用自己写遮罩层。

两个容易写错的地方：

- **放大要另拼一条地址，指向 `/card-image` 全尺寸那张，不能直接复用预览框里的 `src`。**
  框里那张走的是 `/card-thumbnail`（长边 200px 的 WebP，13KB）—— 拿它去全屏就是糊的，
  而放大的全部意义就是看清细节。实测同一张卡：缩略图 13KB / 200px，全尺寸 590KB / 400px。
  两条地址的查询参数完全一样（`password` / `code` / `rarity` / `altIndex`），
  只是 `buildCardImgUrl` 的 `thumb: false` 换个端点。
- **图没找到时不许放行。** 那种情况下框里显示的是「图源里没有 XXX.jpg」的原因文字，
  点开全屏会是一片空白 —— 用户只会以为图挂了。所以 `@tap` 里先判
  `!editFormPreview || efPreviewErr` 直接 return，角标和 `cursor:pointer` 也一起跟着条件走
  （没图还给手型，点了没反应，看着就像按钮坏了）。

## 卡牌目录页的「删除卡包」

一级包列表里每张卡片右上角有个 🗑。空包（只在 `_index.json` 里、没有目录行的）和有数据的包都能删。

一次删除动三处，**不可逆**：`cardcatalogs` 里该包的全部目录行、`_index.json` 里的条目、
`{包名}.json`；图源里的图片目录**只搬不删**。

| 口径 | 做法 |
|---|---|
| 包里还有实物卡 | **直接禁止**，弹窗只给红字原因、不给「确认删除」按钮。要先去清库存 |
| 卡图文件 | 整个目录 `rename` 进 `{ocgDir}\_deleted-packs\{时间戳}\{包名}\`，真文件留着 |
| `cardmarks` | **一条都不删**。删完会出现在一级底部「有 N 条登记不属于任何卡包」的提示里 |
| `carduniques` | **一个字不碰** —— 那些身份跨几十个包共用，按包删会毁掉别的包 |

> 回收目录为什么放在 `_deleted-packs`（下划线开头）：`/uncataloged-packs` 会过滤掉
> `_` / `.` 开头的目录，所以刚删掉的包**不会**又在「图源里还有 N 个包未收录」里冒出来。
> 同盘 `rename` 也不会跨卷。要捞回来就去那个目录下按时间戳找。

### 判断「这个包有哪些卡」不能只看包名

`cardcatalogs.packCode` 和编号前缀**不是一回事**，实测有 41 行两者不一致：
`packCode` 是 `BETB(+1)` 而它下面编号的前缀是 `BETB`；`packCode` 是 `2006` 而编号前缀是 `WC6`。

所以删除范围按 `packCode` 走（`deleteMany({ packCode })`），但**禁止条件必须再把前缀算进来**：
先 `distinct('code', { packCode })` 拿到这个包真正拥有的编号，再取它们的前缀做 `^前缀-` 的正则兜底，
两支取并集。宁可比该删的多拦几个（让用户先去清库存），也不能漏掉一个留下孤儿卡。

前缀进正则前必须转义 —— `(+1)` 里的括号是真元字符，不转义的话 `ZZPAR(+1)` 会被当成
「`ZZPAR` 后面跟一个或多个 `1`」，把 `ZZPAR1-001` 这种不相干的卡也一起拦下来。

### 和「改编号」一样的两道保险

1. 点 🗑 先发一次只读的 `dryRun`，把影响面摊开再问一次（删几行目录、搬几个图、留几条登记、图片去哪）。
   空包不能因为「目录行 0」被拒 —— 那正是它要被删的原因。
2. 备份落在 `Server\Storage\delete-pack-backup\{时间戳}\`（`_index.json` / `{包名}.json` /
   `cardcatalogs` 三份快照），审计写 `Server\Storage\delete-pack-audit\{时间戳}-{包名}.json`。
   ⚠️ 备份目录的键是**时间戳**，不是审计 id（审计 id 是 `时间戳-包名`），按审计 id 去找会找不到。
3. 执行顺序：**目录行 → `_index.json` → 包 JSON → 图片目录**。图片放最后（最贵最不可逆），
   前面任何一步失败都**不回滚**已经完成的部分，只记进 `warnings` 返回给前端 —— 跟改编号同一个道理，
   已经删掉的行有备份可查，为后面某一步把整包数据再造回来反而更糟。

## 「图源设置」页的「数据备份」：导出 / 导入

「卡牌目录」里三样东西都是人工整理出来的成果，所以要把它们**捆成一个文件**带走：
`cardcatalogs`（卡牌目录 31969 条）+ `cardmarks`（信息登记 94 条）+ `alt-labels.json`（异画标签）。

| 按钮 | 干什么 |
|---|---|
| 📤 导出 | 下载 `slan-catalog-{日期}.json`，一个文件装齐上面三样 |
| 📥 导入 | 选一个这种文件 → 先只读核对 → 弹窗让你选**合并**还是**覆盖** |

**合并导入**（默认，保守）：只写文件里**有的**记录，库里多出来的一条都不删。

> `$set` 的判据是「这个键在不在文件里」，不是「值空不空」—— 你特意清空的字段要能被导入覆盖。
> 唯一的例外是 `note`：**空备注不覆盖已有的备注**。备注是人一条条写的处理说明，
> 拿一份旧备份导进来就把之后新写的说明冲掉，那是人的劳动，比其它字段都金贵。

**覆盖导入**（危险）：先自动整份备份，再清空重建 —— 「这份文件就是全部」。
异画标签里文件没提到的编号会一起消失。所以点了以后还要再确认一次，确认框里会写清楚
会清掉多少条、备份落在哪。

- 备份落在 `Server\Storage\pre-replace-backup\{时间戳}\before-bundle.json`，
  **导错了拿它再导一次就能退回来**（用覆盖模式）。
- 目录名走 `uniqueDir()`：同一秒连点两次不会算出同一个目录，第二份不会盖掉第一份 ——
  这份备份是导错后唯一的退路，不能丢。
- ⚠️ 但**弹窗里那个路径只是预告**：真导入时若那一秒已被占，会顺延成 `…-2`。
  真正那份以导入完成后告诉你的为准。

导入后会自动 `invalidateTcgCaches()`，目录和图片立刻刷新，不用重启后端。

> **这条链路只会在页面层暴露的坑**（接口测试直接打 `/api/tcg/...` 时一路绿灯）：
> 数据包 7.6 MB，远超全局 `express.json({limit:'5mb'})`，所以要在全局解析器**之前**
> 给 `import-bundle` 单独挂一个 128 MB 的。前端 `apiBaseUrl` 是 **`/v1/api`**
> （`request.get('/tcg/x')` 拼出来是 `/v1/api/tcg/x`），而接口测试习惯直接打 `/api/tcg`。
> **两个挂载点都得挂**，只挂一个的话另一个方向就是「导入永远失败」，
> 而且失败得很安静（5 MB 那个先拒掉，根本到不了路由）。
> 别的路由**不能**跟着放宽 —— 放宽的是这一条导入路径，不是全局上限。

## 后台的「立即备份 / 恢复」为什么曾经一直是坏的（V1.2.56）

后台面板上那两个按钮走的是 `mongodump` / `mongorestore`（`Server/src/routes/admin/backup.js`）。
在 V1.2.56 之前，那两条命令是这么拼的：

```
mongodump    --db s-lan-local --out "<目标>"
mongorestore --db s-lan-local --drop "<源>"
```

**都没带 `--host` / `--port`** —— 于是它们默认去连 `localhost:27017`，而本项目用的是
**28018**。结果：点「立即备份」等半分钟，回一句 `备份失败: MongoDB 未运行或导出出错`。
（那句笼统的提示也是坑的一部分：真实原因 `failed to connect to mongodb://localhost/` 就摆在
`mongodump` 的 stderr 里，被吞掉了，整整一个版本没人看出是「连错端口」。）

两个后果：

- **V1.2 从来没成功备份过一次。** `V1.2\Storage\backup` 下那些老备份是 V1.1 时代做的
  （当时库在 27017），**里面没有 `carduniques` 和 `cardmarks`** —— 拿它们恢复会丢卡名和全部
  「信息有误」登记。判定方法很简单：看备份里有没有 `mongodump/<库名>/carduniques.bson`。
- **恢复那条更危险。** 它带 `--drop`。现在连不上所以只是失败，但**万一 27017 上真跑了个
  MongoDB，它就会连上去把那个库的表 drop 掉** —— 删的不是本项目的数据，所以出事了都反应不过来。

V1.2.56 的修法：**主机 / 端口 / 库名一律从 `config.mongodbUri` 解**（那个值本来就跟着
`MONGODB_URI` 走，默认 `mongodb://127.0.0.1:28018/s-lan-local`），四条路径
（列表筛选、导出、恢复的源目录、恢复命令）统一用同一份。另外：

- 失败时把 `mongodump` / `mongorestore` 的最后一行 stderr 原样报出来，不再吞
- 失败时收掉本次刚建的空壳目录 —— 但**只收自己建的**。`stamp()` 只精确到秒，
  同一秒里点第二次会落到同一个名字上，那种情况下那个目录装的是**上一次成功备份**，
  无脑删会把好的删掉（这行是验收脚本当场抓出来的）
- `backup.js` 顶上那句「备份根目录: V1.1\Storage\backup」的注释也是错的，一并改掉：
  算出来的是 `V1.2\Storage\backup`，**V1.1 里那 19 份老备份这个页面看不见**

> 换机器 / 大改之前，先确认这个页面能列出备份、且最新那份里有 `carduniques.bson`。

## 「卡牌目录」页的「新建卡包 / 传图 / 导 Excel」

一级页搜索栏右边有个「＋ 新建」（**不放顶栏** —— 顶栏左侧到居中标题只剩几十像素，再塞会挤歪）。
建包做两件事：在图源里建目录 + 往 `_index.json` 里登记一条。**不写后面这条，一级列表里根本看不到它**
（`GET /packs` 只读 `_index.json`）。

建完自动进二级。包是空的，顶上会出现一张引导卡：这个包的图源绝对路径、命名规则、
`_` 前缀会被忽略，以及最要紧的那句「**罕贵度必须和表格里填的一字不差，否则卡片会显示成卡背**」。
引导卡下面三个入口，外加一个拖放区（把图直接拖到页面上就行）：

| 入口 | 接口 | 限制 |
|---|---|---|
| 📁 打开目录 | `/pack-files/:包名/*` | 复用「卡牌地址」那套图源目录浏览 |
| ⬆️ 上传图片（也可拖放） | `POST /pack-files/:包名/upload` | 一次 ≤200 个、单个 ≤20MB、只收 `.jpg/.jpeg/.png/.webp`、`_` 前缀跳过、**同名不覆盖只报告** |
| 📊 导入 Excel | `POST /packs/:包名/import-excel` | 中文表头、表头行自己找（说明行可有可无）、卡密必须纯数字 |
| ⬇️ 下载 Excel 模板 | `GET /template.xlsx` | 带一行说明 + 一行示例 |

上传结果的弹窗会原样摊开**跳过的那几个**和跳过原因（下划线、扩展名不对、同名已存在），
不会只说一句「完成」。

导入结果的弹窗把三件事分开说，也**不会只说一句「导入成功」**：

- 新增 / 对上库里几行
- ⚠️ **哪几行的罕贵度和图源里的文件名对不上**（带 Excel 行号）。这类错**不报错**，
  只会让那张卡安静地显示成卡背 —— 是最难事后查的一种，所以必须单独列出来
- ❌ 卡密不是纯数字之类被拒的行，**带 Excel 里看到的那个行号**

> 「图源里一张图都没有」的编号只记个数汇总报（`其中 N 个编号在图源里还没有图片`）——
> 新包批导几千行时逐行警告会刷屏。
> 同一张表导第二遍，报的是「更新 N」而不是「新增 0、更新 0」：用的判据是 `matchedCount`
> 而不是 `modifiedCount`，字段值一字不变时后者会报 0，看起来像白导了。

### 一级底部的「图源里还有 N 个包未收录」

图源里有 1555 个包目录，`_index.json` 里只有 ~929 个。差的这 600 多个**不铺进一级列表**
（一级保持 929 个，找包才快），但也不能让它们真的消失：

- 底部一行提示把两种「对不上」分开说：
  **图源里有文件夹、目录里没收**（点进去有图，只是没登记）／
  **目录里有、图源里没文件夹**（点进去是空包 —— 换了盘符或网络盘没挂上就是这个症状，
  这一类才是真要处理的）
- 点开是清单，**点其中任意一个能直接开它的目录浏览**。这条路径不经过 `_index.json`（按包名
  直接读盘），所以这是那些包唯一可达的入口。

> 新建卡包时若包名**已经在 `_index.json` 里、但图源里找不到目录**，会被**拒掉**，
> 而不是顺手建一个空目录：写包会把 `full_name` 合并进去，同时把 `status` / `total_cards`
> 覆盖成空值 —— 那样会抹掉一个本来有数据的包的元信息（换个盘符就能触发）。

### 三个只有上真机才会撞到的坑

- **`fs.renameSync` 跨盘会抛 `EXDEV`**。图片先落到 `Server\Storage\upload-tmp\` 再搬进图源，
  而**图源路径是用户可配的** —— 配到别的盘或网络盘就是跨盘，`rename` 直接失败，
  用户拿到的是一句英文报错。所以搬运统一走 `moveFile()`：先试 `rename`，
  `EXDEV` 就退回复制 + 删源。
- **multer 报错时，它自己已经写下去的文件不会删**（它是边解析边落盘的）。
  超限、字段名不对、连接中断都会留下 `.part` 残渣。所以上传路径两头都要兜：
  `uploadGuard` 包一层，出错时把 `req.files` 里已经落盘的**全删掉**；进处理函数第一件事
  是把 `req.files` **全部**登记下来，这样不管后面从哪个分支返回，`finally` 都能清干净。
- **拖放监听挂在 `document` 上**，所以小程序/APP 里 `document` 是 `undefined`，
  挂之前要先判一句（挂不上也不该挂）。H5 里 `uni.showModal` 是**普通弹窗、有真 DOM**，

## 「卡牌目录」页的图：只认图源里对得上的那张

瓦片取图以前是**两级候选**：① 编号+罕贵 → 服务端的精准层；② 落空后只拿卡密再要一次

| 有图 | 服务端按 `{编号}-{罕贵}[-{异画号}]` **整段命中**到文件 | 绿 |

## 执行链补上包级守卫：已确认的包不许再被批量拉起（V1.2.76）

V1.2.75 把「已确认 = 只读」落到了后端，但**只落在行级接口上**（`queues.js` 的 `取条目`，
它管 `rerun` / `remove` / `remove-all` / `mark-listed` 那几个按钮）。而**真正批量改行的是
另两条路** —— `auto-execute.js`（PC）和 `auto-execute-vm.js`（VM），它们从不走 `取条目`：

```js
const queueItems = await ListingQueue.find({ batchId, userId }).sort({index:1}).lean();
const pendingItems = 范围.filter(it => it.itemStatus === 'pending' || it.itemStatus === 'failed');
```

于是整批那枚「一键上架」（只发 `batchId`，不带 `packCode`）照样会把**已确认包里跑红的行**
重新拉起来跑。后果比"多跑一张"严重：跑崩了 `finally` 会把 `running` 打回 `pending`，那个包
就成「**已确认、却有一行没跑完**」——被 `包们` 滤出待上架屏、又进不了归档判据，用户在详情里
是只读、看不见那行，只剩「放回」一条路自救。**正是 V1.2.75 想堵掉的那个软死锁，从另一条路
又漏了回来。**

### 改法：两条执行链取行前先读档案，同口径补齐

两条链在读完 `queueItems` 之后、圈范围之前，各加同一段（逐字一样，注释互相指认）：

1. `ListingBatch.findOne({batchId, userId})` 取 `state` + `donePacks`；
2. `state === 'listed'` → `409`「这一批已经确认完成（归档）了，不能再跑」；
3. 点名 `packCode` 命中 `donePacks` → `409`「先把它『放回待上架包』再跑」；
4. 圈完范围后，把已确认包**整包滤掉**（整批那枚按钮就是走到这里的），并记下滤掉了哪些包；
5. 一行都不剩、而且是因为包被确认掉的 → `409` 明说
   「没剩下可跑的行 —— AAA、BBB 已经确认完成了，要跑就先把它『放回待上架包』」，
   **不是**回一句 `success: true` 让人以为跑完了。

包名口径跟前端 `组包()` 一字不差：`it.packCode || String(it.code).split('-')[0] || '未知'`。

**顺序有用意**：`packCode` 的 409 放在滤范围**之前**，先把话说清楚；滤范围放在 `startIndex`
筛选**之后** —— 起点管的是"index 从这行往下"，跟包确认与否是两件事，两个筛子次序换了结论一样，
但读起来容易混。VM 链的守卫块放在 `sc.ensureConnected()` **之前**：被拒的请求一帧 ADB 都不发。

### 建档口径

- **`donePacks` 只增不减地影响执行**，但「放回」一按就恢复 —— 守卫读的是实时档案，不是快照。
- **没有档案的老批次**（`findOne` 回 `null`）行为与改动前**一模一样**，不受影响。
- 失败（红）行**不再被阻塞重跑**这件事没有变：只要那个包**没被确认**，红行照样会被拉起来跑。

### 验证方式

离线桩测（`%TEMP%\slan-verify\_v1276-guard.cjs`）：照 memory `server-route-testable-without-restart`，
在 require 路由文件**之前**把 `ListingBatch` / `ListingQueue` / 两条执行链的执行器 / `screen` /
`listingRunLock` / `ws` / `auth` 全塞进 `require.cache`，从 `router.stack` 按 `route.path` 掏出真
handler 直接喂 req/res。**不重启 4002、不连数据库、一条 ADB 都不发**。两条链各 6 组断言共 42 条：
整批滤掉已确认包、点名已确认包 409、归档批次 409、全确认完时的专用文案、以及两组"没档案 /
没确认过任何包"的回归（证明老行为没动）。

> 桩要注意的一个坑：**VM 链读的是 `config/listing-flows-vm/` 那一份流程，不是 PC 的
> `config/listing-flows/`**。桩里吐的状态字必须跟那一份流程成功路径上的字对上，否则整批都被
> 判失败、断言成了假失败。（本节写于 V1.2.76，当时 VM 两份流程的顶层配的是
> `successCode: "输入成功99"`；找错了目录会查成 `undefined`、退回默认 `成功99` 而误判。
> **V1.2.97 起两份 VM 流程的成功字已统一成 `成功99`、顶层不再配 `successCode`**，
> 详见上面 V1.2.97 那节。）

## 上架价打底改用「价格(输出)」，并把 VM 流程的成功码对齐（V1.2.97 · 补丁1）

三处改动，都是围绕**一键上架跑完一行之后怎么收尾**。代码只动了一行，其余两份是 VM 流程的
配置数据。

### 1. 上架价打底：从「集换价」换成「价格(输出)」

`auto-execute-vm.js` 跑完一行、**判成成功**之后，会给这一行的「上架价格」（`listingPrice`，
页面上每行右端那个小输入框）打底。原来拿的是**集换价**（`outputJhj`），现在换成
**「价格(输出)」**（`outputPrice`）—— 也就是「详细」面板里归在**「上架内容」**那一组的
「价格」，流程靠搜 `商品价格` 关键字抠出来的那个值。

**只改了 `auto-execute-vm.js:312` 的第一个实参**。`services/listingOutputs.js` 的
`给上架价打底` 本身是个"给我一个价串、这行空着就填进去"的通用函数，不关心传进去的是哪个价，
所以**函数体一个字没动**，函数形参仍叫 `集换价`（名字已名不副实，但改它会牵动注释，这次没碰）。

颗粒度，别记混：

- **一行一价** —— 每个队列行有自己的 `listingPrice`，不是整批一个价
- **只在 `isSuccess` 分支里执行** —— 判失败时连打底都不会跑（所以成功判定坏了，打底也就等于没有）
- **只在该行 `listingPrice` 为空时才填**（`''` / `null` / 字段不存在三种都算空），
  用户手填过的一律不冲 —— 这条由 `$or` 交给数据库判，不是先读后写
- **对已有数据零影响**：已经填过的行不会被重写，**只有以后跑的新行**按新规则走，不用做迁移

> ⚠️ **没做兜底**：`价格(输出)` 抠不到的行**不会**打底（旧版至少还能退回集换价）。
> 流程里 `商品价格` 这个关键字比 `集换价` 更容易抠空（VM 流程B 就是因为不稳，才另加了
> 第 42 步「提取添加商品页面价格与数量」再取一次），所以这一类行要**手填**。
>
> PC 侧的 `auto-execute.js:283` 有同样一行，**这次没动** —— PC 那份流程压根不产生
> `价格(输出)`，跟着改反而会打不上底。

### 2. VM 流程的成功码：`输入成功99` → `成功99`

VM 的两份流程（`config/listing-flows-vm/流程A-新建.json`、`流程B-更新.json`）靠一条
`setvar` 步骤把状态字写进 `运行状态(输出)`。**成功路径上写的是 `输入成功99`**，而后端判成功是

```js
const 成功码 = String(flow.successCode || '成功99');   // auto-execute-vm.js:295
const isSuccess = status === 成功码;                    // :300 —— 严格相等，不是 includes
```

V1.2.63 本来给两份流程的顶层都配了 `"successCode": "输入成功99"` 来对上，**但那个字段一直在丢**：
流程编辑器的保存**只发 `name` / `desc` / `steps` 三个字段**
（`flow-editor-vm.vue:493`），服务端又是照单全收
（`listing-agent-vm/index.js:111` 的 `{ ...req.body, name }`）—— 整份文件被重写成这三个字段，
**顶层其它字段一律不留**。于是在设置页保存过一次流程之后，成功码就退回了默认的 `成功99`，
而流程里写的还是 `输入成功99`，两个字之差 → **整批全判失败**，并且把 status 原文当错误信息
显示出来（`:349 errMsg = status`），页面上看到的就是「输入成功99」这种"报错"。

这一版把**流程里那两个字改掉**（`template: "成功99"`），让它跟默认成功码对上：

- 改的是 **`steps` 数组里的 `template`**，而 `steps` 是编辑器保存时会**完整往返**的部分 ——
  所以**以后再在设置页保存多少次都不会再丢**。这比"把 `successCode` 补回顶层"更耐用
  （顶层字段补回去，下次保存照样没）。
- 两份流程里各有 9 / 12 处写 `运行状态(输出)`，**只有成功那一处是 `输入成功99`**，
  其余是 `报错A01-编号` … `报错B11-比较集卖价2`，一个字都没动 —— 它们是用来分辨失败原因的。
- 后端仍会打一行 `流程「…」没有 successCode，退回按「成功99」判成功` 的 warn（顶层确实没配），
  **这是预期的**，结果是对的。

> 顺带一提，`end` 步骤**不能**当成功判据：它只让**执行器**返回 `success: true`
> （`listing-agent-vm/executor.js:276`），而批量层根本不看 `result.success`，
> 只用上面那个字符串相等。流程走到底、`end` 返回了 `true`，照样可能被判失败。

### 3. 这条链的连带关系（踩过一次，记下来）

`isSuccess` 为真时才会做三件事：标 `success` → **给上架价打底** → **标记实体卡「已上架」**。
判失败时三件全跳过。所以第 2 条那个成功码一旦对不上，后果不只是"显示成失败"：

- 那一行标成 `failed`，要人工重跑
- **实体卡没被标 `listed: true` → 进不了订单凑库池**（凑库只认 `listed: true`，见 V1.2.87）
- 上架价也不会打底

也就是说，**第 1 条的改动只有在第 2 条修好之后才真的会执行到**。

### 为什么走撤回接口，而不是手工覆盖 `stockcodes`

原计划是手工按 V1.1 覆盖 `stockcodes`。实测后发现那样会**留下一份自相矛盾的状态**：
库已经解锁回 `pending`，可 `listingqueues` 里 8564 行任务清单还在、批次档案还是
`state: 'parsing'` —— 一键上架页会一直显示「这批在上架中」，点进去 8564 条清单俱在。

改用应用自带的 `POST /v1/api/listings/queues/:batchId/revert`，它是照 snapshot 逐库还原的
正规路径，顺手把队列、批次状态一起收干净：

```
HTTP 200
{ "libCount": 1588, "queueDeleted": 8564, "cardsRestored": 0, "cardsMissing": 0,
  "收回已上架": 0, "auditId": "20261003-001001-listing-revert-26-10-2-2" }
```

`cardsRestored: 0` 是对的 —— 这个批次 `auditStamp` 是**空串**，`要还原卡 = isListed || !!auditStamp`
两侧都不成立，所以路径根本没经过卡位号和原图。

一个容易看漏的点：撤回**不还原 `currentCards` 快照值**，它用 `Card.countDocuments` 的**现数**
（`queues.js:378`）。所以 `A0-002-02` 被写成 20（现数）而不是快照里的 21 —— 这正是我们要的，
否则计数会跟实际卡数对不上。

## 「恢复」点了没反应 —— H5 连续两次 `uni.showModal` 会被单例的收尾吃掉（V1.2.95）

用户报「点恢复之后没有恢复成功」。**后端没问题、鉴权没问题、路径也没问题** ——
是**请求根本没发出去**，卡在第二个确认弹窗上。

- **现象**：点「恢复」→ 第一层「恢复备份」弹窗正常 → 点「继续」→ **弹窗一闪就没了**
  （约 300ms），既不报错也不执行，网络面板一条请求都没有。
- **根因（uni-app H5 的锅，不是业务代码）**：`uni.showModal` 是**全局单例**，
  连续调用第二次会复用同一份 DOM。第一次弹窗的**淡出收尾**（Vue 的 v-show + transition
  会把 `display:none` 延到过渡结束才落）大约 300ms 后执行，正好把刚复用上来的第二个弹窗
  一起打成 `display:none`。实测：点「继续」后 +200ms 标题已变「最终确认」、可见高 144，
  +400ms 就 `display:none`、可见高 0 —— 单例被就地改写后又被收尾带走的典型样子。
- **另一个坑（同一段代码里）**：`editable: true` 与 `content` **不能同时用**。
  H5 的实现把 `content` 既当 textarea 的初值、又在渲染时写回输入值，用户打的字会被冲掉，
  `res.content` 永远等于 `content` 那句提示语（≠`'YES'`）→ 只会弹「已取消」。
  想给提示语就放 `title` / `placeholderText`。

**改法**：二次确认（输入 YES）不再用 `uni.showModal`，改成**页面自己的浮层**
（`pages/admin/backup-manager.vue` 的 `askYes` / `askText` + 一个真 `<input v-model>`），
第一层「恢复备份」仍用原生弹窗（单次调用不受影响）。浮层里写明这次备份的时间、
红字警告「恢复后新产生的数据会丢失」，输入大写 `YES` 才能点「确定恢复」。

顺带修了 `components/LocationPicker.vue` 的 `onRename` —— 它也是 `editable` + `content`
同用（`content: item.code`），H5 上会把新名字冲回旧编号，落库等于把库名改成它自己的编号；
现在去掉 `content`、当前名字移到 `title`。**注意这个函数目前全仓没有任何调用点（死代码）**，
「改库名」的入口根本没接上，所以线上并没有被这个 bug 伤到。

验证（headless Edge，`/restore` 请求**拦下来只记录、绝不真发**）：

- 输入 `yes`（小写）→ 提示「要输入大写 YES 才能恢复」，浮层留着，**不发请求**；
- 输入 `YES` → 真发出 `POST /v1/api/admin/backups/20261002-232607/restore`
  （body `{"confirm":"YES"}`）→ 提示「恢复完成，请重启后端」，浮层关闭。

> ★ 排查时的一个教训：headless 里我一开始用**真键盘事件**敲字，一直敲不进去
> （`document.activeElement` 停在 `BODY`）—— 那是因为弹窗当时是 `display:none`，
> 元素压根不可聚焦，**这本身就是「弹窗没显示」的旁证**。改用「原生 value setter +
> `input` 事件」才把字送进去。键盘敲不进去别急着怪探针，先看看目标元素可不可见。

### 为什么是纯前端 Canvas，不另起 Python / 不装插件 / 不加后端路由

- 卡图接口 `/api/tcg/card-thumbnail`、`/api/tcg/card-image` **免鉴权、跟页面同源** →
  画进 canvas 不污染画布，`toBlob` 能正常导出（跨域图会让导出直接失败）；
- **中文用浏览器自带字体，零字体配置** —— 服务端 `sharp` 写中文要装中文字体，那是这条路上
  最大的坑（`sharp` 在 `Server/package.json` 里躺着，但全仓只做过单图缩略图，
  `.composite(` / `.text(` 零命中，没有可照抄的合成代码）；
- 保存用现成套路 `Blob` + `<a download>`（同 `pages/admin/tcg-paths.vue`）。

代价是**只能在 H5 跑** —— `document` / `canvas` 是浏览器 API。所以按钮和 `import` 都用
`#ifdef H5` 圈起来，App 端连代码都不进包。

### 两个必须做对的地方

- **行数多了要分张**。单张 canvas 的 device 像素上限约 16384px（超了不报错、直接给一张空白），
  按行高 244px 算 30 行就到头。代码按 `设备上限 16000 / k` 反推每张行数，超了自动切成
  `清单_<单号>_1of3.png`、`2of3`… 逐张下载。
- **图必须先加载完再落笔**。`await` 完写进 `已加载图`（同步可读的 Map），画的时候从那里取；
  否则导出的 PNG 会缺图。单张图 8s 超时，挂一张就画灰块占位，不许把整张长图拖死。

图源优先用**原图**（`card-image`），404 时退回列表用的缩略图（`card-thumbnail`），
再不行才灰块 —— 只做路径段字符串替换，编号/罕贵/卡密原样带过去，不用再问一次目录。

## 点「凑库解析」图变卡背：`catImg` 写在了渲染之后、而且绕过了 Proxy（V1.2.88）

**症状**（用户原话）：「然后在我点击凑库解析的时候它卡牌图片它又变成了那个颜色他又变成了那个呃
只有那个叫卡牌背面那个图片了」。同一屏**刷新一下图就回来了**。

V1.2.86 把卡图接上了目录（`origImg || catImg || 卡背`）。但**只要人在详情屏里原地重载**，
三张卡就齐刷刷变回卡背 —— 凑库解析、改卡、换品相、通过/撤回，凡是在详情屏里调
`loadOrderDetail()` 的路径全都中招；而**首次进详情**（`selectOrder`）却是好的。这正是
「不刷新就不出图」的真身，V1.2.86 之后那次无头复现没抓到它，就是因为只走了首次进入那条路。

### 根因：两件事叠在一起，缺一不可

`loadOrderDetail` 原来是这么写的：

```js
currentOrder.value = data          // ① 赋值当场触发一次渲染
await 回填卡图(data.cards || [])   // ② 异步：问目录拿到卡密后，往 **data.cards（原始对象）** 上写 catImg
```

- **① 渲染得太早**：`回填卡图` 是异步的（要 POST `/api/tcg/cards` 问卡密），
  赋值那一刻 `catImg` 还是 `undefined`，`卡图(c)` 只能返回卡背。
- **② 回填写得无效**：写的是 `data.cards` —— **原始数组**。Vue 3 里 `currentOrder.value` 是
  `reactive(data)` 的代理，往原始对象上写属性**绕过了 Proxy 的 set 陷阱**，不会通知渲染副作用。
  于是①那一帧卡背**再也不会被重画**，就永久停住了。

`selectOrder` 之所以没事，纯粹是运气：它是 `await loadOrderDetail(...)` **跑完才**切
`viewMode = 'detail'`，等于「渲染之前就挂好了」。注释里那句「详情屏没这个坑 —— 它 await 完才切过去」
把这份运气当成了保证，所以只在列表那条路上防了同一个陷阱。

### 改法：先挂图、再整体赋值

```js
const data = await getOrderDetail(orderNo, fresh)
await 回填卡图(data.cards || [])   // 先往原始对象上挂好
currentOrder.value = data          // 再赋值 —— 第一次渲染就带着图
currentOrderNo.value = data.orderNo
```

顺序倒过来，**过渡的那一帧卡背直接没有了**，也就不需要靠 Proxy 的通知去补一次重画
（同 `inventory.vue` 的「拼好整对象再赋值」）。`拉目录` 内部对网络失败是逐批 `continue`、
不抛异常（见 `cardDb.js`），所以这一步不会把详情本身拖住。

列表屏（`loadOrders`）不能照搬：它是 `concat` 追加，屏上已有老订单不能推倒重建，
所以仍用「从 `orders.value` 代理上取、就地写 `catImg`」那条写法 —— 两处注释互相指了路。

## 凑库解析改从「已上架」取货：`{ listed: false }` 是一句写反了很久的条件（V1.2.87）

## 订单处理 / 总管理库 / 信息登记页不再恒卡背：`Card.img` 是个 0% 填充的死字段（V1.2.86）

顺着 V1.2.85 往下查「还有哪面没出图」，发现同一个根因在**另外三页**上更彻底 ——
库存页是「取图取错了地方」，这三页是**整条链上拿的全是恒空字段**。

### 根因：`Card.img` 永远是空的

`Card.img` 在**建卡时就被写死成 `''`**（`routes/cards/index.js`，`POST /cards` 根本不看请求体里的 `img`）。
清库前那个快照（38,767 张）里的填充率：

| 字段 | 填充率 | 是什么 |
|---|---|---|
| `Card.img` | **0.00%** | 死字段，永远空 |
| `Card.origImg` | 99.88% | 实拍原图 `/uploads/orig/*.jpg`，**真在用** |
| `Card.extCode` | 0.11% | 识别流程的快照，权威值在 `cardcatalogs.extCode` |

所以**每一处 `card.img || CARD_BACK` 都是结构性恒卡背**，跟数据无关。命中的四处：

| 页面 | 原来的图源 | 死在哪 |
|---|---|---|
| 订单处理（列表框 / 详情行 / 拣卡扁平图 / 放大预览） | `OrderCard.img` | 凑库时从库存卡抄 `Card.extCode` 或 `Card.img`，两条腿都空 |
| 总管理库（组缩略图） | `subCards[0].img` | 服务端聚合 `img: '$img'`，就是 `Card.img` |
| 信息登记包内页 | `CardMark.img` | 登记时对 `Card.img` 拍的快照 |

### 改法：官方图**前端按编号现拼**，不落库

真实卡图不在库里，是磁盘上 `images\OCG\{包}\{编号}-{罕贵}.jpg`，按编号+罕贵走精准模式取。
拼 URL 需要一个**合法卡密**过门（`card-image` / `card-thumbnail` 开头那道卡密检查是路径穿越防线，
卡密会被拼进 `YGOPro\{卡密}.jpg`，空串直接 400），而卡密是**目录**的属性 —— 同一编号的所有实体卡都一样。

于是口径统一成三件事：

1. **按编号问目录**：`拉目录()` 从 `inventory.vue` / `auto-listing.vue` 那个重复两份的本地函数
   提到了 `Client/src/api/cardDb.js`，四个页面共用（`POST /api/tcg/cards`，每批 200 串行）。
2. **现拼、不落库**：拼好的地址挂在页面的临时字段上（订单页 `catImg`）。存进 `order_cards`
   会随目录更新而过期 —— 卡密是目录的属性，快照没有意义。
3. **优先级**：`实拍原图 origImg` > 目录现拼的官方图 > 卡背。实拍原图仍是第一顺位。

服务端那边同步**拆掉了一台造不出东西的机器**：`routes/orders/index.js` 凑库时原来会试着拼
`/api/tcg/card-image?password=${pc.extCode}…`，而 `pc.extCode` / `pc.img` 都是死字段，
恒得空串 —— 看着像在做卡图，其实什么都没做。现在那儿只留 `origImg`，
`OrderCard.img` 的注释也改成「恒为空，字段留着只为不动已有文档与响应形状」。

## 库存管理页不再整页卡背：卡密改按编号问目录（V1.2.85）

首页「库存管理」进去的页（`pages/inventory/inventory.vue`，标题写的正是**已上架库**）
上架完之后整页都是卡背。查下来不是数据坏了，是这一页**取图取错了地方**。

### 卡背是怎么来的

`inventory.vue` 拼图地址只用**卡文档自己**的卡密：

```js
const imgUrl = c.extCode
  ? buildCardImgUrl({ password: c.extCode, code: c.code, rarity: c.rarity, altIndex: altIdx })
  : (c.img || CARD_BACK)          // ← 空卡密就落这儿
```

而 `c.extCode` 是**识别流程从实卡上认出来的副产品**，绝大多数卡上是空的 ——
清库前那个快照（`s-lan-test`，38,767 张卡）里 `extCode` 非空的只有 **42 条**（0.1%）。
`img` / `origImg` 同样为空，于是每一格都落到 `CARD_BACK`。

`cardDb.js` 那边还有一道：

```js
if (!password) return ''          // 没有卡密就没有地址
```

所以实测那一页 33 格**一次 `/card-thumbnail` 都没请求过**，只发过一条 placeholder 的请求。

### 图片根本不在数据库里

图源是磁盘文件（`images\OCG\{包}\{编号}-{罕贵}.jpg` 详细图、`images\YGOPro\{卡密}.jpg` 保底图），
MongoDB 里两个集合各管各的：

| 集合 | 存什么 | 定位图用得上吗 |
|---|---|---|
| `cards` | 实体卡：`serial` / `code` / `rarity` / `condition` / `extCode` | 只有编号和罕贵 |
| `cardcatalogs` | 卡牌目录：一行 = 编号 × 罕贵度，带 `packCode` | **编号就是钥匙** |

后端 `card-thumbnail` 找详细图的 key 就是 `${code}-${rarity}`（`findOcgExact`），
**卡密压根不参与挑图**。那为什么还非给不可？因为路由开头有一道门：

```js
if (!卡密合法(extCode)) return res.status(400).json({ error: 'password 参数不合法…' });
```

它是**路径穿越防线**（卡密会被拼进 `YGOPro\{卡密}.jpg` 当文件名），空串直接 400。
实测：

| 请求 | 结果 |
|---|---|
| 只给 `编号+罕贵` | **400** password 参数不合法 |
| `password=目录卡密` + `编号+罕贵` | **200**，9,760 字节 WebP 真图 |
| `password=目录卡密` + 罕贵度写错 | **404**「图源里没有 301-008 的 UR」 |

### 改法：照自动上架页的口径，按编号问目录

卡密是**目录**的属性 —— 同一编号的所有实体卡卡密都一样。自动上架页（`auto-listing.vue`）
一直是这么取的，所以同一批卡在那边有图、在这边没有。

这一版把 `inventory.vue` 里那段「每个编号发一个请求问 `/api/tcg/card`」换成了
`POST /api/tcg/cards` **分块串行（每批 200）** —— 跟自动上架页的 `拉目录()` 同一口径。
顺带治掉一个老毛病：原来 `uniqueCodes.map` 全打出去，一页几百个编号会把同域连接占满，
把图片和别的接口一起饿死（V1.2.83 在别处治的就是这个）。

取卡密的优先级：**卡文档上那个 > 目录那个**。卡上是识别出来的、最贴这张；
没有再问目录要。两个都没有才回 `c.img || CARD_BACK`。

> 为什么卡密取哪个都不影响出哪张图：给了 `code + rarity` 时后端走**精准模式**，
> **只认 `{编号}-{罕贵}` 整段命中**，卡密在那儿只负责过门。罕贵度填错照样 404 显形 ——
> 这是那一页注释里写的「报错了就该显形（图变卡背）」，这条**没动**。

### 顺带修的一处：按卡密搜索

`groupMap[key].extCode` 原来存的是 `c.extCode`（空的），而 `applyFilters` 就是拿它
跟搜索词比的 —— 图上按目录卡密出得来了，搜那个卡密却搜不到，等于修一半。
现在存的是「页面上认的那个卡密」。

### 怎么验的

无头 Edge + CDP 打真 4002、真库、签 002 的 token，只读 GET：

- 改前：33 格**全卡背**，发出的图请求只有 1 条 placeholder，`/card-thumbnail` 0 条。
- 改后：**33 格全真图**，`naturalWidth` 全是 200（后端缩略图的目标宽度），
  33 条 `/card-thumbnail?password=…&code=…&rarity=…`，0 格卡背，0 异常。
- 搜索：弹窗里填目录卡密 `37101832` → 33 格收成 1 格，正是 301-008。

> 探针上踩的坑：`uni.showModal` 带 `editable: true` 时，H5 里是
> **`textarea.uni-modal__textarea`**，不是 `input`。按 `input` 找会一个都找不到。

改动只在 `Client/src/pages/inventory/inventory.vue` 一个文件，**没动后端**（一个新接口都没加）。

## 「已上架」从子页签升成顶栏第 4 枚（V1.2.84）

自动上架页的顶栏原来只有三枚：本地库 / 云端库 / 待上架库。已上架的包委屈在「待上架库」
底下当**子页签**（`待上架包 | 已上架包`）。这一版把它拎出来，顶栏变成四枚平级：

```
本地库   云端库   待上架库   已上架库
                        └── 原来这里还有一层「待上架包 | 已上架包」，收掉了
```

### 为什么是"整体搬"，不是"拆开"

「已上架」那一屏装着**两种**包：

| 来源 | 是什么 | 数据从哪来 |
|---|---|---|
| `staged` | 本批已点过包级「确认完成」、还没归档的 | **当前队列** `队列items` 派生 |
| `archive` | 历史已归档批次的 | `GET /listings/archives` |

`staged` 那一撮是从**当前批次**长出来的，而且「整批完成」（归档）和每张卡片的「放回」
都挂在这一屏上。只把 `archive` 搬到新页签、把 `staged` 留在待上架库，等于给同一份队列数据
维护两套出口 —— 多一层会漂的状态。原样整体搬过去，代码里那 20 处 `sub === 'listed'`
判断**一个字都不用改**。

### 关键改动：`sub` 从独立 `ref` 变成 `topTab` 的派生值

```js
const sub = computed(() => (topTab.value === 'listed' ? 'listed' : 'pending'))
```

子页签收掉之后，「上架包 / 已上架包」就等价于「待上架库 / 已上架库」两枚顶栏页签了。
没把那 20 处读 `sub` 的分支逐个改成 `topTab === 'listed'`，而是保留 `sub` 这个名字、
把它变成派生值 —— **真源只剩 `topTab` 一个**。两个 `ref` 各自维护，才是以后一定会漂的那种写法。

唯一两处写 `sub.value` 的地方：`切块()`（随子页签一起删掉）和归档成功后的
`sub.value = 'listed'` → 改成 `topTab.value = 'listed'`。
**这个漏不掉**：computed 没有 setter，写漏了这一步当场就报错。

原来第一屏写的是 `v-if="topTab !== 'listing'"`（本地库 / 云端库列表）。

点「已上架库」看到的是本地库的卡片。改成显式列白名单：

```html

```

`switchTab` 里 `'listing'` 与 `'listed'` 走同一段（两个都要 `checkAndRestoreQueue()`：

### 文案

搬家之后「已上架包」这个名字**不存在了**，还留着的话 App 会把人指到一个没有的页签上。

## 自动上架页不再压 8562 个请求：目录改成批量查（V1.2.83）

「点什么都卡」的成因不是"数据太多"，是**取数方式**。真库实测一个批次：8564 行 / 8562 个编号。

进页面要按编号拉目录，原来 `拉目录` 是**一编号一个** `GET /api/tcg/card?code=`：

```js
await Promise.all(codes.map(async (code) => { ... fetch('/api/tcg/card?code=' + ...) ... }))
```

8562 个编号就是**同时压 8562 个 HTTP**。浏览器同域只开 6~10 条连接，其余全部排队 ——
整页的图片、别的接口一起被饿死，表现就是"点哪个页签都卡"。

**后端单次 `/card` 本身一点都不贵**（1 次按 `code` 索引的 find + 内存里 10 分钟 TTL 的
`卡名.回填` + 按包目录缓存 30s 的 `listOcgRarities`）。问题在**请求数**，所以解法是
"一次多带几个编号"，不是"把单查做快"。**8562 → 43 次。**

### 后端：抽出共用件 + 新增 `POST /api/tcg/cards`

- `buildCardPayload(rows, qRarity, ocgDir)` 从 `GET /card` 里抽出来，
  **单查与批量查共用这一份**。两处各写一份的话形状必然慢慢漂移，而前端是照这个形状读的
  （`拉目录` 认 `jp_name`，卡片库认 `rarity` / `alt_labels` 拼 `cataKey`）——
  漂一格就是"全变未找到"或"异画全错"。**这是本次最大的回归风险**，所以有一条专门的
  形状对齐断言（下面"怎么验"里说）。
- `POST /api/tcg/cards`，body `{ codes: [...] }`，**单次上限 200，超了 400**。
  - 用 POST 不用 GET+CSV：200 个编号拼 query string 会撞 URL 长度上限。
  - **不带 auth**：跟它替代的 `GET /card` 一致 —— `拉目录` 的 fetch 本来就不带 token。
  - **一次 `$in` 把全部编号查出来**，绝不按编号循环 `find`（那只是把 43 次请求换成
    8562 次数据库查询，把瓶颈从网络搬到库上）。卡名也**一次回填全部行**。
  - 返回 `{ ok: true, cards: { <原样串>: card }, missing: [<原样串>…] }`。

**★ 键必须是请求里那个原样字符串**（不 trim、不大写，归一化只用来查库）。
前端 `名称表` 的键是 `item.code` 原值，拿归一化后的大写当键会让它**一条都命中不上** →
整批变"未找到" → 红边 + `blocked` → **归档被判据拦死**（`包可确认 = !p.缺.length && p.没跑 === 0`）。

**★ `missing` 只在成功响应里出现**。前端据"有没有 `missing`"决定要不要把编号记进 `未找到`。
失败响应里带上它，一次网络抖动就会被读成"这些编号在目录里真没有"，把整包标成不可上架。
所以失败分支只有 `{ ok:false, error }`，一个 `missing` 都不带 —— 前端那边也配了一句
`if (!d || !d.ok) continue`。

### 前端：按 200 精确分块，且失败时一个都不写

```js
const 每批编号数 = 200
for (let i = 0; i < 要查.length; i += 每批编号数) { ... }   // 串行切片，不是 Promise.all
```

「查过的跳过、查不到的记住」那条逻辑保留（`if (code in 表 || code in 没) return`），
所以**只有第一次进页面是全量拉**，之后切页签再回来基本全命中内存。

### 量到的效果（真库真图源，只读复核）

600 个真编号：**3 次请求 / 223 ms**，600 个全部命中，逐字节与单查一个字段都不差
（40 个随机真编号深等比对）。真批次 8562 个编号按同样口径是 **43 次请求**。

### 这一版**没动**的同类地方

- `onParseAll`（「解析待上架卡」那枚按钮，`:1076`）与 `inventory.vue:163` 是同一款逐编号循环。
  它们的数据量由"待解析的卡"决定、不是 8562，且各自动作独立 —— **另开版本再改**，不塞进这一版。
- 页签切换仍会重下整份队列（`/queues/:batchId` 8564 行 / 5.89 MB）。这是**另一条**独立的
  卡顿来源，要单独一版（见下）。

### 怎么验

两份离线脚本，都在 `%TEMP%\slan-verify\`，都不起服务、不重启 4002：

- `_v1283-tcg-cards.cjs`（桩测，46 条断言全过）：`tcgPaths` 指向**临时目录**并把包目录
  真造出来（`AAA-001-01-SER.jpg` + `-SER-1.jpg`），所以异画统计那条是**真跑的**，不是桩返回值。
  覆盖：一次 `$in` 查全部（不是按编号循环）、原样串当键、200/201/空数组的上限、
  失败响应里**没有** `missing`、以及 ★★ 单查与批量查逐字节深等。
  最后一组把 `.vue` 里的 `拉目录` **源码切出来包成函数真跑一遍**：8562 个编号 →
  43 次请求（`Math.ceil(8562/200)`），网络全断时 `未找到` 仍是空的。
  > 切源码时注意：`const 每批编号数` 声明在 `拉目录` **外面**那一行，得一起切进来，
  > 否则 `ReferenceError: 每批编号数 is not defined`。

## 撤回只收回自己标的卡：给「已上架」标记一个专用身份（V1.2.82）

V1.2.78 让「跑成功就自动把实体卡标成 `listed`」，V1.2.79 让「撤回时把它收回来」。
收回那一步靠 **`listedPrice` 和 `listingId` 都是 `null`** 来认领"这是我标的卡" ——
**这个判据不成立**：

- `Card.listedPrice` 默认就是 `null`；
- 「主库」`master-library/index.js` 标记时写的是 `listingId: listingId || null`，
  而它的调用方 `master-library.vue` **根本不传 listingId** → 落库同样是 `null`。

于是**人工在「主库」标的卡**和**一键上架标的卡**在库里逐字段同形。撤回把人家的标记
一起清成 `listed:false`，而订单凑库只认一句 `{ listed: false }`（`orders/index.js:486`，
**不看库状态**）—— 那张真人已经在店里挂出去的卡，会被当成库存再拣一遍，**同一张卡卖两次**。

（注释里写的"主库会写 listingId"只在调用方传了的时候成立，而调用方没传。）

### 改法：写标记的时候点名是谁标的、哪个批次标的

`Card` 上加两个字段，`services/listingMarkListed.js` 是唯一的读写口：

```js
listedBy:      { type: String, default: null },  // 'auto-listing' | 'master-library' | 'listed-cards'
listedBatchId: { type: String, default: null },  // 一键上架专用：哪一批标的
```

- **收回**按 `{ libraryCode: {$in: 这批锁的库}, userId, listed: true, listedBy: 'auto-listing', listedBatchId: 本批 }`
  筛 —— 人工标的（`listedBy` 是别的字）和别的批次标的都**不在范围内**。
- 仍然按**库范围**收，不按 `serialList`：归档 3.3 的 `compactLibrarySerials` 重排过卡位号，
  队列里的 `serialList` 早对不上现在的 `Card.serial`。全仓没有任何路径会改 `Card.libraryCode`，
  所以库范围不会"搬库漏收"。
- `标记已上架` 里那句 `listed: { $ne: true }` 守卫**保留**，而且它在这里有第二层意义：
  一张已经被「主库」人工标过的卡会被**跳过**，于是**不带**本功能的身份，撤回时也就不会被误收回 ——
  正是要的行为。

### 三个数，不是一个

撤回响应多两项：

| 字段 | 含义 | 正常值 |
|---|---|---|
| `收回已上架` | 真收回来几张 | ≥ 0 |
| `未收回已上架` | 本功能标过、**但不是这一批**的（含没有批次号的旧标记） | **0**，非 0 才要报警 |

后端另外单独查一个 `他标`（`listedBy` 是别的字的，主库/上架记录标的、以及加字段之前的旧标记），
**只记日志不报警** —— 那是常态，把它并进"还剩 N 张没收"里天天响等于不响。

`未收回已上架` 非 0 时，前端撤回成功的提示里会**多弹一个框**点名，并指路「主库」的「取消已上架」。
非 0 的那张卡仍是 `listed:true`，凑库拣不出来 —— 卡在、就是卖不掉，得人工放回来。

### ★ 另两条写 `listed:false` 的路也必须清身份

这条不做，等于**换个条件重演同一个 bug**。全仓只有两处写 `listed:false`，都补了
`listedBy: null, listedBatchId: null`：

- `master-library/index.js` 的 `mark-unlisted`
- `listed-cards/index.js` 的 `unmarkCards`（单条删除与清空两条路都走它）

反例链：批次标的卡 → 主库「取消已上架」（只清 `listed`、**留下身份**）→ 主库又「标记已上架」
把它标回 `listed:true` → 身份仍是那一批的 → 撤回认旧身份把它当"自己标的"打回凑库池 →
**一张真人挂过的卡又被卖一次**。

顺带把 `listed-cards/index.js` 的 `POST /batch` 按编号分组写 `listedPrice`（单条那条路本来写了，
批量漏了；当前无调用方，属预防性一致），并写明 `listedBy: 'listed-cards'`。

### 已知边界（代码不兜，靠这两句）

1. **部署瞬间在飞的批次**：它的标记是旧代码写的、没有身份 → 上线后撤回这批会**一张都收不回**
   （归到"他标"而不报警，因为代码分不出它是"别人的"还是"没身份的自己的"）。
   一批之隔的小坑，撤回时看那句 `未收回已上架` 就知道。
2. **「主库」全标会无条件重写 `listedAt`** —— 新字段救不了，也不该救（那是人工动作）。
3. **同一张卡不要跨批次重复上架、也不要乱序撤回**。代码按"库范围 + 批次号"认领，
   不维护每张卡的批次历史。

### 验证方式

离线桩测（`%TEMP%\slan-verify\_v1282-listed-identity.cjs`，41 条断言全过）：
照 memory `server-route-testable-without-restart`，require 路由文件**之前**打桩，
从 `router.stack` 掏真 handler。与上一版不同的是 `Card` 桩换成了一个**真的按 filter 筛选的内存小集合**，
所以「B2 批次的卡不被 B1 撤回命中」「人工标的卡不在过滤范围内」是**真的落库比出来的**，不是看过滤条件猜的。
除两条执行链、人工标记、归档兜底、撤回响应之外，专门有一组是**防回归身份残留**的：
断言 `mark-unlisted` 与 `DELETE /listed-cards/:id` 的 `$set` 里必须带 `listedBy: null, listedBatchId: null`。

> 桩的坑：`掏()`（= require 路由文件）**必须在打桩之后**。路由是在模块加载那一刻把模型抓走的，
> 先 require 再换 `require.cache` 已经晚了 —— 会报一个看着像产品 bug 的
> `Cast to ObjectId failed ... for model "ListedCard"`。

## 执行中不许撤回（V1.2.81）

`拦执行中`（`listingLock.isRunning(batchId)` 一问就 409）原先挂在四个入口上：
`remove` / `remove-all` / `rerun` / `mark-listed`。**`revert` 是漏的那个**。

后果不是"数据脏"，是**实打实的对外动作**：撤回会

- 把这一批的队列 `deleteMany` 删掉；
- 把库状态照档案快照还原（回到 `locked`/`pending`，也就是"没上架"）；
- 把本功能标的「已上架」标记收回（V1.2.78）。

可正在跑的那条链还在驱动模拟器**往店里点** —— 库这边已经判回没上架，模拟器那边还在挂卡、
还在点确认。同一张卡的两边认知彻底分叉。

### 改法

在 `revert` 的前置检查里补一句，口径跟 `拦执行中` 一字不差（它定义在文件下方，
`revert` 在它上面，所以直接问锁）：

```js
if (listingLock.isRunning(batchId)) {
  return res.status(409).json({ error: '这一批正在执行中，先终止再撤回' });
}
```

**只管进程内这把锁，不管库里停在 `running` 的行。** 后者是"上一次跑崩了留下来的"，
正是最需要撤回自救的时候（那种行的正规出口是先点「重跑」，但撤回不该被它挡住）。
页面上的「撤回」按钮本来就写着 `v-if="currentBatchId && !listing"`，这个守卫补的是
**另一台设备 / 另一个页签**同时动手的那条缝。

### 一条**刻意不加**的守卫：`price` 改价不拦

评审里把「`price` 也该补 `拦执行中`」跟这条并列，**这是错的，没改**。
`price` 的注释里本来就写着为什么不拦，而且理由在代码里立得住：
打底那一步（`services/listingOutputs.js` 的 `给上架价打底`）的过滤条件是

```js
{ ...filter, $or: [{ listingPrice: '' }, { listingPrice: null }, { listingPrice: { $exists: false } }] }
```

—— **"只在空的时候填"这个判断落在数据库那层**，不是"读出来比一比我该不该写"。
所以跑着的时候人改的价，无论跟打底的先后顺序如何，最后都是人改的那个值留下。
加一个 409 只会白白少掉一个能力。

### 验证方式

离线桩测 `%TEMP%\slan-verify\_v1281-revert-lock.cjs`：把 `listingRunLock` 桩成可控的开关，
验「在跑 → 409 且一个字都不写」「不在跑 → 照样撤得动」「入口其它守卫不变」，
外加一组**防回退**断言：执行中改价必须仍是 200。

## 整批跑绿之后刷新页面，这一批就凭空消失（V1.2.80）

### 症状

跑完一个包、**还没点「整批完成」**的时候按一下刷新（或者切到别的页签再切回来），
待上架屏变成空的：包没了、`currentBatchId` 空了，「整批完成」那枚按钮也画不出来
（它要 `currentBatchId`）。库既没归档，也不在任何一屏上 —— 只能靠「撤回」瞎试。

### 原因：`/queues/pending` 的口径

`GET /v1/api/listings/queues/pending` 的筛选是

```js
itemStatus: { $in: ['pending', 'running', 'failed'] }
```

它只列**还有没跑完的行**的批次。而"整批都跑绿了、就差归档"的批次，
一条这种行都没有 —— 于是它**不在名单里**。前端恢复进度只认这一个接口
（`checkAndRestoreQueue`），刷新就等于把这批丢了。

这跟 V1.2.75 之后的节奏正好撞上：用户是**一个包一个包跑的**，
跑绿的包越多，这一批离"pending 行没有"就越近 —— 越接近要归档的时候，越容易一刷新就丢。

### 改法：加一条兜底，不动 `/queues/pending` 的口径

```js
// ① `/queues/pending` —— 跑了一半的批次
// ② `/batches?state=parsing` —— 跑绿了还没归档的批次（上面那条根本不列它）
const 试接 = async (batchId) => {
  if (!batchId || !(await 拉队列(batchId))) return false
  currentBatchId.value = batchId
  return true
}
```

- 先按老路走（接上半成品批次），接不上再走兜底；`拉队列` 失败（批次被删/被撤）就换下一批。
- 兜底那条按 `createdAt` 倒序（后端就是倒序），所以接的是**最近**那一批。
- **没有改 `/queues/pending`**：它的语义是"还有活没干完的批次"，
  PC 主机面板（`pages-pc/listing-host`）拿它当"待跑队列"看，混进跑绿的批次反而是错的。

## 归档死在半路就再也救不回来：把「死结」拆成三条都能走的出口（V1.2.79）

### 死角长什么样

`POST /listings/batches/:batchId/complete`（「整批完成」）动手的顺序是：

```
3.1  StockCode.updateMany({listingBatchId: batchId}, {$set:{status:'archived', listingBatchId: null}})
3.2  Card.updateMany({...}, {$set:{origImg: ''}})
3.3  compactLibrarySerials(lib)        ← 重排卡位号
3.4  ListingBatch.updateOne({...}, {$set:{state:'listed', auditStamp: stamp}})
```

**两条命根子都在 3.1~3.3 里被改掉，而开锁的钥匙 3.4 才写。** 只要中间断一次
（进程崩、磁盘满、ADB 那边把服务带倒……），这一批就三头堵死：

| 想干什么 | 撞到什么 |
|---|---|
| 再点一次「整批完成」 | 按 `listingBatchId` 查库 → **0 个** → `400`「这一批名下一个库都没有，档案和库对不上，先别动」 |
| 点「撤回」自救 | `revert` 读 `readSnapshot(batch.auditStamp, …)`，而 `auditStamp` **还是空的** → `500`「归档时那份卡片快照找不到了」 |
| 直接看库 | `status` 已经是 `archived`（进不了「待上架库」那屏的判据），批次号又被清空（进不了归档判据）——**两边都不认它** |

而快照文件其实好端端躺在 `Server\Storage\carduniques-backup\<戳>\cards-before-<批次号>.json`，
**只是没有任何一行代码记得住那个 `<戳>`** —— 原图和旧卡位号就这样变成了事实上的丢数据。

### 三处改动

**① `auditStamp` 提到动手之前写（新的 3.0 步）**

```js
// 三、动手 的开头，3.1 之前
await ListingBatch.updateOne({ batchId, userId: req.user.id }, { $set: { auditStamp: stamp } });
```

代价只有一次 `updateOne`；3.4 再写一遍同一个值（幂等）。从这一刻起，
"这批动过卡位号和原图"这件事在库里留了痕，撤回才找得到那份快照。

**② 归档查不到库时退回档案快照**

```js
const 锁定 = [...new Set(locked.map(s => s.fullCode).filter(Boolean))];
const 快照候选 = [...快照].filter(c => !锁定集.has(c));
const 被别人锁 = /* fullCode ∈ 快照候选 且 listingBatchId 既不是 null 也不是本批 */;
const codeList = [...锁定, ...快照候选.filter(c => !被别人锁.has(c))];
```

档案里的库快照跟"锁定那批"本来就是**同一个集合**（`queues.js:72` 先按 `lockList` 抄进
`snapshot`，`:137` 再按同一个 `lockList` 上锁），所以拿它兜底是准的。
唯一要扣掉的是**现在挂在别的批次名下**的库 —— 那说明这批被撤过又重新解析了，不属于这次。
锁定集为空时会打一行 `console.warn`，事后对得上账。

**③ 续跑**绝不重拍快照**

`batch.auditStamp` 有值 == 上次死在半路。这时候库里现在的卡位号/原图是**上一趟压实+清空之后**
的样子，再 `saveSnapshot` 一张盖上去，就把唯一那张回退依据换成了废纸。所以续跑只
`readSnapshot` 把原档**读回来核对**（读不到/是空的 → `500`，跟"快照没写成功不许动手"同一条规矩），
本次尝试的审计日志另开一份（`openAudit(makeStamp(), …)`），`begin` 里照记用的是哪张快照。

**④ 撤回的「要还原卡」判据放宽**

```js
const 要还原卡 = isListed || !!batch.auditStamp;   // 原来只看 isListed
```

半归档的批次状态还停在 `parsing`，原来会被当成"没归档过的批次"直接跳过卡片还原 ——
库状态回到 `pending`，卡位号和原图却留在归档后的样子，**不报错的部分还原**，最难查。
戳记只有归档那条路会写，所以「有戳记」正好等于「这批动过卡位号和原图」。
从没归档过的老批次没有戳记，行为一个字不变。

### 顺带说清一个既有事实

`compactLibrarySerials` 是**幂等**的（把卡按 1..n 重新编号，跑两遍结果一样），
所以"接着上次跑完"这条路是安全的，不会因为压实过两遍而错位。

### 验证方式

离线桩测 `%TEMP%\slan-verify\_v1279-deadlock.cjs`：归档 4 组 + 撤回 3 组，
含一条**事件流顺序断言**（`拍快照 → 写戳记 → 归档库`，证明戳记确实在动手之前）和
两组回归（没归档过的老批次撤回时不许碰卡片快照／已归档批次读不到快照仍须 500）。

## 跑成功就把实体卡标成「已上架」：堵掉同一张卡被卖两次（V1.2.78）

### 症状

订单凑库的筛选条件只有一句（`routes/orders/index.js:486`）：

```js
const q = { listed: false };     // 不看库状态、不看批次、不看有没有在卖
```

而「一键上架」跑成功一张，**只写了队列行**（`ListingQueue.itemStatus = 'success'`），
`Card.listed` 一个字没动。于是那张卡在店里已经挂出去了，在库里还是"可凑库"的库存 ——
**订单凑库照样能把它拣走，同一张实体卡卖两次。**

实测（2026-10-02 只读查真库）：跑成功的 8 行涉及 **25 个卡位号**，这 25 张**一张都没标**；
全库 38766 张卡里 `listed:true` 是 **0 张** —— 这条路从来没标过。
（原先只有「上架记录」那条人工路径会标。）

### 改法：新增 `Server/src/services/listingMarkListed.js`，四个调用点

`标记已上架({ serialList, userId })` —— 拿**卡位号**当钥匙，一句话搞定：

```js
Card.updateMany(
  { serial: { $in: 号们 }, userId, listed: { $ne: true } },   // $ne 让整件事幂等，也不冲人工的时间戳
  { $set: { listed: true, listedAt: new Date() } }
);
```

**为什么用卡位号**：`ListingQueue.serialList` 存的就是这一行压着的实体卡位号
（`A0-000-00-0001`），跟 `Card.serial` 一一对应 —— 真库 8564 行**行行都带号**，
抽查 300 个号命中 300 张卡。而且卡位号是**物理**身份，跟库搬不搬迁无关。
（不按 `code + libraryCode` 兜底：同库同编号常有多张实体卡，那样会误伤。）

四个调用点：

| 在哪 | 什么时候 | 说明 |
|---|---|---|
| `auto-execute.js` PC 链成功分支 | 跑成功那一刻 | 位置在「上架价打底」之后 |
| `auto-execute-vm.js` VM 链成功分支 | 同上 | 与 PC 版逐字一样 |
| `queues.js` `mark-listed` | 人点「已经手工上架了」 | 那行既然真上架了，卡就该退出凑库 |
| `batches.js` 归档 3.2b | 点「整批完成」时 | **兜底**，扫的是本改动之前跑成功的行（就是上面那 25 张） |

**归档那条必须在 3.3 压实卡位号之前** —— `compactLibrarySerials` 一跑，`Card.serial`
就跟 `serialList` 对不上了，那时候再标只能标个空集。代码里有一句断言位置其实是在
测这个顺序（事件流 `card.updateMany → card.updateMany → 压实`）。`failed` 的行**不标**：
它们真的没上架。

### 顺带补上的反向动作：撤回要把标记收回去

`listed` 是**另一个开关**，撤回（`queues.js` 的 `revert`）原先只还原库状态、卡位号、原图，
不碰它。可撤回的语义是**整批作废**、这些库重新回到可凑库的池子里 —— 刚标上去的 `true`
不收回来，这批跑成功过的卡就**永远拣不出来**了（订单只认 `listed:false`，
库里也没有界面能翻回来，只有主库那个「取消已上架」的逃生口）。卡不是丢了，是静默卖不掉。

所以 `revert` 加一步 3.2b：`取消已上架({ libraryCodes })` ——

```js
{ libraryCode: { $in: 库们 }, userId, listed: true, listedPrice: null, listingId: null }
```

两个 `null` 是**边界**，不是凑数：本功能只翻 `listed`/`listedAt`，另两条路各有自己的记号
（「上架记录」写 `listedPrice`，「主库」写 `listingId`），少了这两个条件，
撤回会把**真人在店里挂出去过**的卡一起打回可凑库 —— 那又变回超卖了。
范围用「这批锁的库」而不是 serialList：已归档那批的卡位号被压实重排过，序列号早对不上。

### 已知取舍（写下来免得以后当成 bug）

- **它不建 `ListedCard` 记录**，只翻 `Card.listed` 这一个开关。「上架记录」那一页要价、
  要上架时间、要来源库，这儿一样都没有 —— 硬塞一条假记录比不塞更坏。
  代价：**「上架记录」页不会因此多出这些卡**，它们只是从"可凑库"里退出来了。
- 标记写库失败**不外抛**（只打日志，带 batchId/index）：那一刻卡已经在店里挂出去了，
  为了这一笔连带把整行判成失败是拿小事掀翻大事。归档时还有一次兜底。

### 验证方式

离线桩测 `%TEMP%\slan-verify\_v1278-listed.cjs`（同 `_v1276-guard.cjs` 的做法，
不重启、不连库、不发 ADB）：两条执行链 + 人工标记 + 归档 + 撤回各一组，
外加共用件本身的空输入/去重/写库失败。**含一条顺序断言**（补标必须早于压实）。

## 已上架屏的头计数改成"数屏幕上摆着的"（V1.2.77）

「已上架包」屏顶上原来那行是：

```js
const 已上架张数 = computed(() => 已上架批次.value.reduce(     // ← 只数**已归档批次**
  (s, b) => s + (b.items || []).reduce((t, i) => t + (i.addQty || 1), 0), 0))
// 模板：{{ 已上架张数 }} 张卡 · {{ 已上架批次.length }} 个批次
```

V1.2.75 给这一屏加了一类包（**本批已确认·待归档**，`来源: 'staged'`），可这行字的来源
没跟着改 —— 于是点完包级「确认完成」，卡片真的跳到这一屏了，**顶上数字却纹丝不动**。
看着像按钮没生效，用户的自查方式是回头再点一遍，容易被引到"是不是没存上"上去。

### 改法

头部改成数**屏幕上真的摆着的包**（`已上架屏包们` 是 staged + archive 的合体），
再把"还没归档"的那部分单独点出来：

```js
const 已上架头文案 = computed(() => {
  const 张 = 已上架屏包们.value.reduce((s, p) => s + p.total, 0)   // ← 数屏幕
  const 段 = [张 + ' 张卡']
  if (已上架批次.value.length) 段.push(已上架批次.value.length + ' 个批次')
  if (待归档张数.value) 段.push('其中 ' + 待归档张数.value + ' 张待归档')
  return 段.join(' · ')
})
```

三种形态：只有已归档 → `12 张卡 · 2 个批次`（跟从前一样）；只有本批确认的 →
`3 张卡 · 其中 3 张待归档`；两种都有 → `15 张卡 · 2 个批次 · 其中 3 张待归档`。

- **`个批次` 一栏没有包时不印** —— 只有 staged 包时写「0 个批次」读起来像出错。
- 盘后不再有 `已上架张数` 这个 computed（改完就没人引用了，留着是死代码 + 一句会骗人的注释）。
- **口径只动这一行字**：`已上架批次` 本身、溯源、详情屏的数据源一个字没动。

## 「一键上架」补上包级「确认完成」：包级搬迁 / 批级归档两级分开（V1.2.75）

「一键上架」原来只有**批级**：一批几百个包，全跑完了才能点「整批完成」把库归档。
可真实节奏是**一个包一个包地跑**（实测：17CC 一张、17PR 四张、18PR 一张、22PP 两张），
跑完一个包想先把它"收起来"，却没有这个动作。于是两处别扭：

1. 17CC 自己写着「可完成」，却没有任何入口能把它搬走；
2. 唯一的归档按钮要等整批跑完才点得亮。

原型 `Client/mock/listing-board.html` 本来就是**两级**的：包卡片右边那枚「确认完成」搬**一个包**，
「整批完成」一次搬**剩下的所有包**。V1.2 落地时只留了右边那块点不动的「已完成」死标记。
这版把两级补回来，并把分工说死：

| 级 | 动作 | 对象 | 实际动到什么 |
|---|---|---|---|
| **包级** | 包卡片右边的「确认完成」 | 一个包 | 只是把它从**待上架包**挪进**已上架包**。库、卡位号、库锁**一律不动** |
| **批级** | 「整批完成」 | 整批 | 才真的把**待上架库**归档进**已上架库**（改库状态、清批次号、压卡位号、清原图）——这一步本来就有，本次只改了文案 |

几个决定，连同理由：

- **标记存后端**（`listingbatches.donePacks: [{pack, at}]`），不存浏览器：刷新不丢、手机/PC 一致、
  能审计。前端只跟 `GET /listings/queues/:batchId` 一起拿（省一次往返，而且标记和队列行是同一份快照，
  不会出现"包搬了但卡还没刷新"）。
- **要能退回**：已上架屏里本批的包右边是可点的**「放回」**，历史归档那批仍是点不动的
  **「已归档」** —— 两种包在同一屏里必须一眼分得开（本批的还带一枚「本批已确认 · 待归档」）。
- **已确认 = 只读**：详情能点开，但没有「标记已上架」「重跑」「上架价格」。这条**后端也兜住**了 ——
  `取条目` 命中已确认的包一律 409。不兜的话 `rerun` 能造出"已确认但又回到 pending"的包：
  它被过滤出待上架屏、又进不了归档判据，而用户在只读详情里看不见那行，只能靠「放回」自救；
  `remove-all` 更狠，删空整个包会让两屏都看不见它，只在库里留一条没有行可指的孤儿标记。
- **归档判据刻意不动**（仍然只看有没有 `pending`/`running`）：有编号查不到目录的包**永远**确认不了，
  真加上"待上架屏必须清空"这条，那种包一出现就永远点不亮归档。**包级标记是加分项，不是归档的前置门。**
  另说一句反直觉的：失败（红）不拦归档，但**没跑过的行照样拦**。
- **只留单包那枚，不做「全部确认」批量键**：原型有 `btnFinishAll`，一次把跑完的包全搬走。
  这版**不做** —— 代价是包多时要一个个点。取舍摆在这儿，将来真嫌烦再加。
- **撤回会把包级标记一并清掉**（跟 `state='reverted'` 同一次写）：撤回要删光这批的队列行，
  留着标记就是一堆孤儿。

接口两个，都挂 `auth`，`state !== 'parsing'` 一律 409：

- `POST /v1/api/listings/batches/:batchId/packs/complete`，body `{ packs: [...] }`
- `POST /v1/api/listings/batches/:batchId/packs/undo`，body `{ pack }`

**服务端不信客户端**：`complete` 只收"这一批里真实存在、且这个包没有 `pending`/`running` 行"的包，
其余在 `skipped` 里点名说原因，前端弹出来。写入走**逐包条件更新**
（`{'donePacks.pack': {$ne: pack}}` + `$push`），不是"读出来改完整个数组写回去" —— 后者两个人
同时点会互相盖。注意这里不能用 `$addToSet`：子文档里带 `at`，值不同就永远判不成重复。

包名算法（`packCode || code.split('-')[0] || '未知'`）在**三处**必须逐字一致
（前端 `组包` / `queues.js` 的 `行的包名` / `batches.js` 的 `包名`）—— 前端按它分组、也按它发「放回」，
漂移了就会出现"点了放回摘不掉"。

## 包详情屏补上「自动上架的起点」（V1.2.74）

「一键上架」的设计稿里一直有这一条：**点任意一行，就从这一行往下跑**。
真程序里没有。查过：`auto-listing.vue` 里「起点」出现 **0 次**，V1.2.61/60/59/58 各版也都是 0，
后端也没有任何「从某张开始跑」的入参 —— 它**从来没落地过**，不是后来改坏的。
V1.2.64（`d37c502`「整页重写」）当时把这条写进了要做的清单，提交时漏掉了，
落地的只有包视图 / 标记已上架 / 溯源表 / WS。这版把它补上，交互照设计稿。

### 怎么用

在包详情屏**点任意一行** → 这一行左边出现一根蓝竖条 + 一枚「起点」签。
点右上角「▶ 自动上架」，就从这一行往下跑到**本包末尾**（上面那些行一张不碰）。
不点行、直接启动 = 从第一行跑，跟从前一样。

- 选中的是**起点**不是开关：再点同一行不会取消它，换到别的包才会清掉。
- 绿色的（已成功）本来就会被跳过，所以起点落在哪一行都不影响它们。
- 点了「标记已上架」之后**起点还在** —— 同包重渲染不做清除，只有**换包**（或进只读的存档包）才清。
- 「急停」之后，起点自动落到**刚停下的那一张**，再点「自动上架」就从它续跑。
  （只在「停的那一行属于当前打开这个包」时才改，不会把你在别的包里设好的起点顶掉。）

### ⚠ 一个行为变化：详情屏那枚按钮从「整批」变成「这个包」

| 按钮 | 位置 | 改后行为 |
|---|---|---|
| 「▶ 自动上架」 | 包详情屏 | **只跑当前这个包**；选了起点就从那一行往下 |
| 「一键上架」 | 包列表动作栏 | **不变，照旧跑整批** |

从前这两枚是同一个动作、发同一个请求（只带 `batchId`）。现在详情屏那枚会多带
`packCode`（+ 选了起点才带的 `startIndex`）。**两个参数都不传 = 整批**，
所以包列表那枚一个字没变。

### 起点用 `index` 当键，不是 `编号|罕贵度`

设计稿用的是 `编号|罕贵度` 两段拼的字符串。这里改用队列行的 `index`：

- 它在**批内唯一**，而且删行之后**不重编号**（`queues.js` 只删不重排），
  所以中途剔掉几行不会让起点指到别的卡上；
- 行上本来就拿它当 `:key`，是天然的稳定标识，不用再造一个键。

后端 `index >= startIndex` 就是「这一行及其之后」—— `queueItems` 已按 `index` 升序，
屏幕上的行序就是这个序。

### PC 版（`:3001` 那条链）的提醒

`auto-execute.js` 也加了同样的两个参数，但**PC 版历来是一批内按罕贵度从小到大跑**
（`N → NR → R → …`），不是照屏幕行序跑 —— 这是既有行为，本次没动。
所以 PC 上「从这行往下」的意思是「**筛出 index 不小于起点的这一批行**」，
筛完仍然按罕贵度排。VM 版没有这一步，就是屏幕顺序。

### 怎么验的

- **后端**：require 真路由文件、从 `router.stack` 掏 handler 直接调，执行器打桩成「只记录不执行」，
  在 `s-lan-test` 里自造 `ZZ-999-XX` 样本，断言四种入参喂进去的条目集合
  （只传 `batchId` = 整批 / 加 `packCode` = 只剩这个包 / 再加 `startIndex` = 只剩这行往后）。
- **前端**：重建 H5 后起临时实例，在真 DOM 上点行、点卡图、点「详细」「×N」「标记已上架」、
  点空图框，确认只有该选中的才选中；截 fetch 的 body，确认两枚按钮发的东西不一样。

## 卡密不再只能是纯数字：`[A-Za-z0-9_-]`（V1.2.73）

「卡牌唯一目录」页的卡密输入框上一直写着「输入 8 位卡牌编码**或者是输入其他的一个代号**」；
「卡牌编号目录」那边却有一条硬校验：卡密必须匹配 `/^\d{1,12}$/`。
两条口径打架很久了 —— 后端报错的原话是「卡密「AT03-JP009」不是纯数字，已跳过」，
前端 toast 是「卡密必须是纯数字」。用户想拿**编号**当卡密用（`AT03-JP009` 这种卡在官方
密码库里查不到，只能自建身份），一直被这道门挡着。**`AT03-JP009` 就是那个现场。**

### 放宽成白名单，而不是放开

```js
/^[A-Za-z0-9_-]{1,64}$/     // 字母 / 数字 / 下划线 / 短横线，1–64 位
```

**不能更宽**：卡密会被直接拼进文件名和 URL ——

- `{ygoproDir}\{卡密}.jpg`
- `{thumbDir}\YGOPro\{卡密}.webp`

所以这道校验本来就是**路径穿越防线**，不是「数字看起来整齐」的美观问题。
`/ \ . :`、空格、以及 Windows 文件名非法字符（`< > " | ? *`）全部排除在外。
验证时专门钉了 `../../etc/passwd`、`a/b`、`a\b`、`a.b`、`a b`、空串、65 位长串七个用例，
在 `/card-image` 和 `/card-thumbnail` 两条路上全部仍然返回 400。

### 8 个校验点收成一份

同一道正则以前散在 8 个地方，改一处漏一处是迟早的事故。现在收成
`Server/src/services/cardPassword.js`（前端对应 `Client/src/api/cardDb.js` 里那份，
**两边必须逐字一致**）：

| 层 | 位置 | 管什么 |
|---|---|---|
| 后端 | `routes/tcg/index.js` `/card-image` | 拼 `YGOPro\{卡密}.jpg` 前的门 |
| 后端 | `routes/tcg/index.js` `/card-thumbnail` | 同上（缩略图那条） |
| 后端 | `routes/tcg/index.js` `buildCatalogDoc()` | PUT 卡包 / Excel 导入写卡密 |
| 后端 | `routes/card-uniques/index.js` `PATCH /row/:code` | 改**目录行**的卡密（用 `卡密可留空`，清空是合法动作） |
| 后端 | `routes/card-uniques/index.js` `PATCH /unique/:key` | 改**身份**的卡密（用 `卡密合法`，非空） |

`POST /card-uniques/unique` **仍然不校验** —— 那是有意的：新增是开一个新身份，形态由用户定；
改名是改已有身份，得守住既有形态。所以带 `/` `\` `.` 的 key 还是存得进来，只是取图那一步
会被上面那道门挡成 400 —— 首尾同一道门，是自洽的。那句老注释
「代价：非数字的 key 取图会 404」也一并订正了，因为**这个代价已经消掉**。

### 顺带：「卡牌唯一目录」的图从「只认 YGOPro」变成两级

那页的图一直只认 YGOPro 图源里 `{卡密}.jpg` 那一张 —— 请求带 `only=ygopro`，
后端见到就短路过去，**OCG 那边一张都不看**。这是有意的（路由里那段注释写着）：
那一行的身份就是卡密，要看的只是「这个卡密在图源里长什么样」，掺进 OCG 详细图反而校不准。

后果是：**用编号当卡密的身份永远出不来图**，只能落卡背 —— 而放宽卡密之后这种身份会变多。
V1.2.73 起改成两级，仍然优先 YGOPro，只是不再一 404 就到底：

```
① ?password=xxx&only=ygopro     → YGOPro\{卡密}.jpg
② ?password=xxx                 ← ① 没有才走这条
      落到普通兜底链的 P1：卡密反查编号目录 → 定位包目录 → 挑第一张
```

第②级挑的**不是随便一张**：`listOcgFiles` 先按 `{编号}-` 前缀把同包里别的卡滤掉，
挑出来的是这个编号自己的图。`AT03-JP009` 在 `OCG/AT03/` 下只有一张，挑到的就是它
（实测 `password=89631139` 不带 `only` 时返回 `OCG/LPST-JP003-PSER.webp`，就是这条链）。

前端用 `@error` 把两级串起来（src 一变浏览器自然会重新请求），**并且因此知道自己拿的是哪一级** ——
第②级命中的会在图的左下角打一个 `OCG` 角标。不打的话，OCG 详细图会被当成 YGOPro 保底图看，
而那正是 `only=ygopro` 当初存在的意义。**后端一个字没改，`only=ygopro` 的语义原样保住。**

**前提**：第②级靠 `CardCatalog.find({extCode})` 反查，所以「卡牌编号目录」里**得有那一行**
（编号 `AT03-JP009`），这一页才出得了图 —— 空手去反查只会一路 404 到卡背。

## 「一键上架」控制台那条 showLoading/hideLoading 警告（V1.2.72）

打开「一键上架」页，控制台会稳定打印一句 uni 的警告：

```
请注意 showLoading 与 hideLoading 必须配对使用
```

来源是 `auto-listing.vue` 的 `onParseAll`（解析那条路）。它把 `hideLoading` 写在
了 `finally` 里，可每条路径自己又各自调了一次：

| 路径 | 原来调了几次 `hideLoading` |
|---|---|
| 没有待解析的卡（提前 return） | 1 次（自己）+ 1 次（`finally`） |
| 正常解析完成 | 1 次（`showToast` 之前）+ 1 次（`finally`） |
| 抛异常 | 1 次（`catch` 里，本次新增）+ 1 次（`finally`） |

多出来的那次在 uni 那边就是「无配对」——它自己也没 loading 可收，于是打印警告。
另外 `uni.showToast` 本身就会把 loading 收掉，所以 `finally` 里那次不止多余，
顺序上也一定排在 toast 之后。

改法：`hideLoading` 只留在每条路径自己那一处，`finally` 里只做 `parsing.value = false`。
同页 `onRevert` / `onComplete` / `onRemoveCopy` / `onRemoveAllCopies` 几处本来就是
「每条路径恰好一次」，没动。

## 「解析结果没能落库」的真身：批次号撞号（V1.2.71）

现象是前端弹一个「解析结果没能落库」，正文却是 `HTTP 500`；再点一次还弹一样的，
当天怎么点都解析不出来。查下来这不是前端的事。

`POST /v1/api/listings/queues` 里生成批次号的是 `generateBatchId`，它当时是这么算的
（`Server/src/routes/listings/queues.js`）：

```js
const last = await ListingQueue.findOne({ userId, createdAt: { $gte: todayStart, $lt: todayEnd } })
  .sort({ batchId: -1 }).lean();
```

**它查的是 `ListingQueue`（队列行），而撤回会把队列行删光**（同一个文件的
`/:batchId/revert` 里那句 `deleteMany`）。于是当天第一批被撤回之后：

1. 当天已经没有任何队列行了 → `last` 是 `null` → `seq = 1` → 又算出 `26-10-2-1`
2. `ListingBatch.create` 撞上 `batchId` 的**唯一索引** → `E11000 duplicate key`
3. 整个请求 500，回包里没有 `batchId` → 前端 `auto-listing.vue` 那个 `else` 分支弹出
   **「解析结果没能落库」**（正文是 `qData.error`，也就是那句 `E11000 …`）
4. 关键点：`ListingBatch` 是只增不删的，那个撞号的档案一直在，所以**当天再也解析不了**

顺带查出同一段里还有两个同源的坑：

- **按 `userId` 过滤** —— 但 `batchId` 的唯一索引是**全局**的（不是 per-user），
  两个用户同一天各解析一次就会互相撞号
- **`sort({ batchId: -1 })`** —— 字符串排序下 `'26-10-2-9' > '26-10-2-10'`，
  当天第 10 批开始又会撞号

改法：批次号改从 **`ListingBatch`**（只增不删）里按 `^<当天前缀>\d+$` 捞出当天全部，
**数值取最大再 +1**，不按用户过滤。另外把建档那一步包成撞号重算重试（最多 5 次），
并发/双击时不会再把 500 丢给前端。

**为什么错误提示会这么误导**：服务端的写入顺序是
`ListingBatch.create → ListingQueue.insertMany → StockCode.updateMany` 全部在
`res.status(201)` **之前**完成，而前端把「发请求」和「回读队列」包在同一个 `try` 里、
两个分支共用一句「没能落库」。所以既有「数据其实落了但回包丢了」的情形，
也有这次这种「服务端一个字都没写但提示说落库」的情形，前端分不出来。

验证现场就是故障现场：库里已经躺着一条 `state:'reverted'` 的 `26-10-2-1`、队列行 0 条。
拿修好的路由 handler 原地跑一次，返回 `201 {batchId:'26-10-2-2'}`，8565 行队列全带
`serialList`、1588 个库锁上 —— 旧代码在同一状态下必定 500。

## VM 侧只剩流程 A / B：删掉那份从没被读过的「流程C」（V1.2.69）

第六步（V1.2.63）留了个口径问题没定：**PC 版**加载 A/B/C 三份流程（`auto-execute.js`），

### 改了什么

- 删掉 `Server/src/config/listing-flows-vm/流程C-更新.json`
- `auto-execute-vm.js` 两处注释改成实话：原来是「VM的B覆盖PC的B+C」，

|---|---|---|

前面十步是一块一块立起来的，各自有各自的验收脚本。这一步做两件收尾的事：
**只用一批把整条路走完**（单点都绿、串起来却坏了的，只有这么跑才抓得到），

### 一、一条龙：解析 → 跑 → 删一份 → 单卡重跑 → 确认完成 → 撤回

`_phase11.cjs`，**50 条断言全绿**。场景故意这么设计：

- 一个库 `Z0-904-01`、两个包（`Z0C904A` / `Z0C904B`）、四张卡
- **删掉的是中间那张（0002）**，不是最后一张 —— 这样「压实」和「还原」才拉得开：
  归档前 `0001/0003/0004` → 压实后 `0001/0002/0003` → 撤回后必须回到 `0001/0003/0004`。
  删最后一张的话，压实前后一模一样，卡位号还原这条就测了个寂寞
- 每一步之后都对**五本账**做断言：库 / 卡 / 批次档案 / 队列 / 审计快照

一路上顺手验到的守卫（都是前面几步加的，这里在真链路上又撞了一遍）：
解析时锁库、还有行没跑完不许归档、库上有没拣完的拣货单不许归档、归档后条目动不了。
最后一条断言是**删掉的那张卡不复活** —— 撤回是「照快照还原还在的卡」，不是时光倒流。

### 二、状态流转总图

#### 库（`StockCode.status`）

| 值 | 谁写进去 | 含义 |
|---|---|---|
| `available` | 管理端新建编号；`syncStockCode` 算出 0 张卡 | 空号 |
| `in_use` / `full` | `syncStockCode`（按 `currentCards` vs `maxCards`） | 有卡在用 / 装满 |
| `pending` | **V1.2 里没有任何代码写它**（只有 V1.1 老数据和撤回的兜底默认值） | 历史态；所有守卫把它和 locked/archived 并列，一律不自动改 |
| `locked` | `POST /listings/queues`（解析），同时挂上 `listingBatchId` | 被某一批占住 |
| `archived` | `POST /listings/batches/:batchId/complete`（归档） | 已上架 |

归档那一笔是 `{ status:'archived', libraryType:'', listingBatchId:null }` ——
**故意不清 `assignedTo`**：管理端认「空号」的判据是 `{libraryType:'', assignedTo:null}`，
归档库要是把归属也清了，就会从「已归档」掉进「编号池」。

`syncStockCode` 只修 `currentCards`，`archived` / `locked` / `pending` 三个状态一律不动。
出库、搬运、合并、释放编号这些动作都会改库上的东西，所以**它们全都得先过
`assertNoOpenPicks(库)`** —— `OrderPick.position` 存的就是 `Card.serial`。

#### 批次档案（`ListingBatch.state`）

```
parsing ──确认完成──▶ listed ──撤回──▶ reverted
```

- 确认完成是**唯一**的归档入口（V1.2.59 起，原来自动归档的判据是坏的）
- 撤回**不删档案**，留着当「这批被撤过」的痕迹；撤回过的批次也不能再确认完成
- 撤回把队列整批删掉、库照 `snapshot` 逐库还原、已归档的还要照
  `cards-before-<批次号>.json` 把卡位号和原图逐张还回去

#### 队列行（`ListingQueue.itemStatus`）

```
pending ──跑──▶ running ──▶ success / failed
   ▲                              │
   └──────── 单卡重跑 ◀───────────┘
failed/success ──人工标记──▶ success（outputStatus='人工标记'）
```

- 「确认完成」只拦 `pending` 和 `running`；`failed` **不拦** —— 删掉还是留着由人决定
- 真跑成功过的行不许用「人工标记」盖掉（会把 14 项输出的来路弄糊）

#### 卡（`Card`）上会变的两个字段

| 字段 | 解析 | 跑 | 确认完成 | 撤回 |
|---|---|---|---|---|
| `serial`（卡位号） | 不动 | 不动 | **压实**（补齐空洞） | 照快照**逐张还原** |
| `origImg`（原图链接） | 不动 | 不动 | **清空**（文件保留在原图缓存里） | 照快照**还原** |

`serial` 是 `OrderPick.position` 认的钥匙，所以任何要动它的地方都得先过
`assertNoOpenPicks`（第 9 步）；库里 `{libraryCode, serial}` 还是唯一索引（同一步加的），
而**撤回是置换**，所以它走的是「先全停到 `TMP-<批次号>-<序号>`、再逐张还原」两段式。

## 「一键上架」落进主程序：第十步 · listed-cards 自己的 bug（V1.2.67）

这一步跟前面九步**不是一路**。`ListedCard` / `ListedSummary` 是另一条更老的路径：
手机/PC 面板跑完一套流程后，顺手往 `POST /listed-cards` 记一笔「这台机器上架了什么」。
它跟一键上架的归档/撤回**不联动** —— 用户早就拍过板：不对齐，只修它自己坏的地方。

坏在哪：它写下去的那笔记录，跟库存卡上的 `listed` 标记**收不回来**。而
`orders/index.js` 凑库时筛的就是 `{ listed: false }` —— 标记退不回去，
这些卡就永远凑不到订单里（卡都在、就是拣不出来）；反过来标记留少了，已经上架的卡
又会被当库存拣走，等于同一张卡卖两遍。

### 一、单条上架用 `updateMany`，不是 `updateOne`

`POST /listed-cards`（单条）原来用 `Card.updateOne`。同一个编号在同一个库里
**可能有好几张实体卡** —— `updateOne` 只挑中其中一张，剩下几张留在 `listed:false` 上。

### 二、两条删除路径都要退标记

`DELETE /listed-cards/:id` 原来只删记录、`DELETE /listed-cards/` 只 `deleteMany`，
**两条都不碰 `Card.listed`**。现在补上，规则是：

- **只在「同编号 + 同来源库」已经没有任何上架记录时才退** —— 同一张卡上架两次、
  删掉其中一条，标记得留着
- 只退 `listed` / `listedAt` / `listedPrice` 三个。`listingId` **不碰**：它不是这条路径
  写的（`master-library` 的 `mark-listed` 才写），不该由这里抹掉
- 没有 `sourceLibraryCode` 的记录什么都不退（面板本来就不传这个字段，
  这类记录从没标过卡）

两条路径的回执里都多了一个 `unmarked`（退了几张），方便对账。

### 三、`DELETE /` 还要清汇总

清空已上架库原来只 `deleteMany` 记录本 —— 汇总表一行不动，数量越攒越虚。
现在先把行捞出来（删完就没得算了），按**行自己的 `quantity`** 减回去，
同一个分组键的行合并成一次减法。卡片标记按「编号 + 来源库」去重后逐个退。

### 四、汇总的键：5 段 → 4 段

```js
// 原来：code|rarity|condition|note|altArt   ← note 连 ListedSummary 的 schema 里都没有
// 现在：code|rarity|condition|altArt
```

key 说按 5 个维度分组，`$set` 却只写 4 个字段 —— 于是「只有备注不同」的两条记录
会各占一行，而任何地方看这两行都一模一样：数对不上，还看不出为什么。
现在 key 和 `$set` 用同一组字段（不同异画仍然分行，这是有意义的维度）。

顺带把两处数量口径统一了：单条 POST 原来给汇总写死 `+1`（行里却是 `Number(quantity)||1`），
批量那条按 `quantity` 加 —— 上架 3 张、汇总只加 1。现在两条路径都按行自己的数量，
删除也从写死 `-1` 改成按行数量减（删掉一条 quantity=3 的记录，汇总就该少 3）。

### 五、一条列名说明（没改列名）

`ListedSummary.altLabel` 这一列存的其实是 **`ListedCard.altArt`（异画）**，不是
`ListedCard.altLabel`。名字是历史遗留；这张表**目前没有任何读取方**
（前端只 `POST /listed-cards`，`GET /stats` 读的是 `ListedCard` 自己），
所以留着旧名、把话写在模型文件头，比改列名更少动干戈。

### 六、代价与遗留（写明白，免得当成 bug）

- **`ListedCard.serial` 不跟着归档/压实更新**：这是「不对齐一键上架」这个口径的
  已知代价 —— 归档会清 `origImg`、确认完成会压实 `serial`，记录本里那笔老账
  仍然写着当时的卡位号
- **汇总表没有 `userId`**：`ListedSummary` 的键是全局的，两个用户上架同一个编号会
  加进同一行。这张表没有读取方，所以没动；真要启用它，得先把 `userId` 补进键里

### 七、怎么验的

`_phase10.cjs`，**36 条断言全绿**，每条都对着一个「改了才会过」的判据：

- A 段：三张同编号的卡 → 单条 POST 后**三张全标**（`updateOne` 只会中一张）
- B 段：同编号同品相、**只有备注不同**的两笔 → 汇总仍是**一行** quantity=4；
  对照组换成不同异画 → 老老实实分成两行
- C 段：删中间那条不退标记（同库还有别的上架记录）；删到同编号同库只剩最后一条时，
  `unmarked:3` 且三张卡的 `listed/listedAt/listedPrice` 全清；汇总按行数量减（4-3=1）
- D 段：`sourceLibraryCode` 为空时**一个卡字段都不碰**（库里另有同名同编号的卡，
  证明不是「库里没这张卡」才没动），但汇总照记
- E 段：清空 → `deleted:2 / unmarked:1`，库 B 的卡退标、两个编号的汇总行成对消失
- F 段：只读三表 39399 / 13883 / 93 全程未动；跑完残留 0

回归：阶段 1–10 各 28 / 36 / 56 / 54 / 54 / 37 / 56 / 42 / 29 / 36 条，全绿。

## 「一键上架」落进主程序：第九步 · serial 重排的统一守卫 ＋ 撞号（V1.2.66）

卡位号（`Card.serial`，`A0-000-09-0007` 这种）在实物上是**不存在的** —— 盒里没有第 7 格，
所以它随时可以压实、可以重排。**但拣货单把这个号当门牌用了**：`OrderPick.position`
存的就是 `Card.serial`。于是每一次「删一张 → 后面全往前挪」都会让还没拣完的单子指错卡，
而且单子自己永远不知道。第八步堵的是「谁能动库」，这一步堵的是「谁能动卡位号」。

### 一、撞号：`countDocuments + 1` 换成 `max(号) + 1`

`POST /cards` 原先拿 `countDocuments({libraryCode}) + 1` 当新卡位号。**库里只要有空洞就撞**
（删过卡、或者压实之前），两张卡共用一个号。抽到 `services/librarySerials.js`：

```js
const nextSerialNum = async (libraryCode, filter = {}) => { /* 取现有 serial 的最大尾号 */ };
const makeSerial = (libraryCode, num) => `${libraryCode}-${String(num).padStart(4, '0')}`;
```

三个分配点全换过去：`routes/cards/index.js` 的新建、`routes/transfer/index.js` 的
`/upload` 与 `/download`（往目标库**追加**，取 `userId: null` / `req.user.id` 各自的口径）。

### 二、重排的守卫：落在 `PUT /cards/:id`

「重编号」这个动作**没有统一入口** —— 它是前端一张一张 `PUT /cards/:id` 打上来的
（`upload.vue` / `batch-recognize.vue` 的 `renumberList`）。所以守卫只能落在这一条上，
别指望某处会统一调 `compactLibrarySerials`：

```js
if (serial !== undefined && serial !== card.serial) {
  await assertNoOpenPicks(card.libraryCode);   // → 409
}
```

**号没变就不拦**：编辑弹窗原样回写整张卡时也会带上 `serial`，那不是重排。

前端跟着改了口径：原来**先把号写进本地数组、再把异常吞掉**，于是服务端 409 拒掉时，
界面上显示的是一堆库里并不存在的卡位号 —— **看着重排好了，其实一张没动**。
现在改成「服务端认了才改本地」，并把被拒张数 `blocked` 回报到 toast 上
（`已删除 N 张；M 张没重排（库上有没拣完的拣货单）`）。

### 三、搬运：只守**源**库

`/upload` `/download` 加 `assertNoOpenPicks(fromCode)`。目标库**故意不守** ——
往目标库放是在现有最大号后面接（第一节的 `max+1`），不动任何人的已有卡位，
谁的单子都不受影响。

### 四、出库：要查**别的**订单在同一库上的未完成拣货单

`orders/index.js` 出库时本来会重排整个库的卡位号，但只查了「本订单」有没有拣完。
漏掉的是：同一个库上可能还挂着**别的订单**没拣完的单子，重排一样把它们指错。

```js
const libsTouched = [...new Set(picks.map(p => p.libraryCode).filter(Boolean))];
// 每库查 pickStatus != 'picked' 且 orderNo != 本单 的条数，> 0 → 409
```

必须 `.filter(Boolean)`（跳过没有库名的老数据），必须排除本单（本单的没拣完正是出库要消费的）。

删卡也从「按 `libraryCode + serial` 找」改成**按 `_id`**：撞号的历史数据上，
按号删会删错卡。删除靠 `OrderPick.stockCardId`（本步新增的 `Mixed` 字段，`models/OrderPick.js`
＋ 一条索引）拿到库存卡的 `_id`，再用原生驱动 `Card.collection.deleteOne` 删
（字符串 `_id` 库上 mongoose 按 `_id` 查会静默匹配 0 条）；老单子没这个字段时
退回按 `serial`、再退回按 `编号+罕贵度+备注`。

### 五、唯一索引 `{libraryCode, serial}`

```
cardSchema.index({ libraryCode: 1, serial: 1 }, { unique: true });
```

加之前先在两个库上查了历史重复：**各 38,767 张卡，0 组重复**。服务启动时的
`syncIndexes()` 会自动把这个索引建出来（现成的非唯一索引会被 drop 掉重建）。
本步在 `s-lan-test` 上**实调**了一次 `Card.syncIndexes()` 断言线上索引真变成 `unique: true`；
真库的索引会在下次后端启动时建上。

### 六、唯一索引当场捅出来一个真问题：撤回是**置换**

索引一上，阶段 3 的回归立刻红了 —— 撤回时逐张把 `serial` 写回原值，而还原本质是**置换**，
写到一半必然出现两张卡共用同一个号（`A0-000-09-0006` 撞 E11000）。

修法是**两段式**：先把这批卡**全部停到临时号**上（`TMP-<批次号>-<序号>`，谁也不撞），
再逐张写到目标号 —— 相当于同时给所有位置腾了地方。

```js
// 第一段：停临时号（顺便探活，matchedCount=0 的记进 cardsMissing）
serial: 'TMP-' + batchId + '-' + String(i).padStart(4, '0')
// 第二段：写到真正的目标号
```

**万一两段之间被打断**，库里会留下一批 `TMP-<批次号>-<序号>` 的卡位号 —— 这个号是
可辨认的（前缀就是批次号），重跑一次撤回即可覆盖；真要对不上，照归档快照
`cards-before-<批次号>.json` 里的 `serial` 手工还原。

（另：快照里 `serial` 为空的老数据**不写回空串** —— 同库两张空号会再撞一次唯一索引。
空号本来就是坏数据，不替它编一个号，只还原原图链接。）

### 七、怎么验的

`_phase9.cjs`，**29 条断言全绿**：

- A 段：有空洞的库上新建卡 → 号接在最大号后，**不撞**
- B 段：搬运往目标库追加、源库有未完成拣货单 → 409；干净库放行
- C 段：出库时**别的订单**在同一库上有未完成拣货单 → 409；本单自己的不拦（对照组）
- D 段：按 `stockCardId` 删卡 —— 把 `stockCardId` **故意指向第二张**，
  断言删掉的是它（旧的「编号+罕贵度+备注」回退会删第一张，这条断言专门用来区分新旧行为）
- E 段：`PUT /cards/:id` 改号 → 库上有未完成拣货单时 409、原号未变；号没变时放行
- F 段：schema 上的唯一索引 + 实调 `syncIndexes()` 后线上索引确为 `unique`

回归：阶段 1–9 各 28 / 36 / 56 / 54 / 54 / 37 / 56 / 42 / 29 条，全绿。
只读三表 39399 / 13883 / 93 全程未动；残留 0。

顺带说一句测试脚本的坑（不是产品问题）：阶段 3 早先几轮失败，部分是**上一轮崩溃留下的
脏数据**（一张卡停在 `0099`、三个库还锁着带旧批次号）—— 是手工修好后才稳定下来的。
还有一处：`Server\Storage\` 里那批审计/快照残留，是因为清理逻辑按「相对本次启动新增」来删，
上一轮崩在同一秒（快照时间戳只到秒）时，那批文件名已经被算进「旧文件」，
既不在删除名单里、也不会让收尾断言变红 —— 现在改成按「文件名里带本轮批号」清。

## 「一键上架」落进主程序：第八步 · 库/卡生命周期的锁与守卫（V1.2.65）

前面七步把「上架批次锁定一个库」这件事立了起来：`StockCode.listingBatchId` 一挂上，
这个库就被那一批占住了。**可是「锁住」只挡了正常的那条路** —— 库里/编号上还有一堆旁门，
每一个都能绕开批次号把库从那一批里抠出来。这一步把这些旁门全堵上，**纯后端，不动页面**。

要理解为什么必须堵：归档入口（`listings/batches.js`）找库的方式是
`StockCode.find({ listingBatchId })` —— **按批次号反查**，不是记名录。所以只要有人
把批次号抹掉、把库的类型改掉、把编号放回池子，那一批就**再也找不到这个库**，
里面已经上架的卡既归档不了、也撤不回来。下面每一条守卫，都是这一个道理的推论。

### 一、`routes/libraries/index.js`：四处补锁

| 位置 | 原先 | 现在 |
|---|---|---|
| `PUT /libraries/:code` | 能直接把库的类型本地↔云端改掉 | 有 `listingBatchId` → 423 |
| `POST /libraries/convert-to-cloud` | 整库转云端，锁形同虚设 | 同上 |
| `POST /libraries/convert-to-local` | 整库转本地，锁形同虚设 | 同上 |
| `DELETE /libraries/:code` | 只看「是不是归档」这一半 | 补上 `status:'archived'` → 423 |

**DELETE 那条**是用户拍板补回来的保护。原先的写法只做到「归档库的编号不释放回池」，
**卡照删不误** —— 于是归档库会变成一个空壳：编号还占着、点进去一张卡没有，
而它占的号既不能重发也没法回池。已上架的东西只有一条退路：「撤回」，不是删除。

### 二、`routes/libraries/index.js`：删掉两处永远不成立的检查

- `convert-to-cloud` 里那句 `if (sc.libraryType === 'cloud') return 409` —— 上面的查询
  已经限定 `libraryType:'local'`，这句永远为假。
- `convert-to-local` 里那句 `if (sc.libraryType === 'local' && sc.assignedTo === req.user.id)`
  —— 同理，查询已经限定 `libraryType:'cloud'`。

两处都留了一行注释写明为什么删，免得下次有人以为是漏了。

### 三、`routes/admin/stock-codes.js`：三个口子

**`applyLabelMigration`（`PUT /:code` 走的那个）不许动 `locked` 的编号。**
原先能改 —— 而 `release` 只拦 `status === 'locked'`。于是有一条现成的绕过路线：
先把 `locked` 改成 `in_use`，再调 `release` 就释放回池了。可它名下的卡还在，
归档入口按批次号反查就落空。现在改 `status` / `libraryType` 一律 423（只改备注之类的放行），
`PUT /:code` 的 catch 也跟着改成尊重 `e.status`（原先一律 500）。

**`release` 补了两件事**：加 `adminOnly`（这个键把编号整个交回池子，谁都可能再领到，
跟同文件其他增删改一个待遇）；拦 `listingBatchId` 非空的行，并在重置时
**把 `listingBatchId` 一并清掉**。清这一下不是洁癖：不清就留下一个**悬空批次号** ——
编号已经回池、别人领到之后 `listingBatchId` 还指着上一批，归档入口会把**那个无辜的新库**
一起卷进那一批。守卫这里刻意**没有**再加归属校验：上面已经 `adminOnly`，
能走到的只有管理员，再写一遍是永远不会执行的死代码（代码里留了注释说明）。

**`merge` 三道守卫。** 合并两头都碰不得 —— 源库要清空回池、目标库要重排卡位：
1. 任一库被批次锁定 → 423
2. 任一库 `status === 'locked'` → 423（同上，锁的状态与实体理论上同生共死，历史数据可能只剩其一）
3. 任一库上有**没拣完的拣货单** → 409。`OrderPick.position` 存的就是 `Card.serial`，
   重排卡位会让这些单子指错卡

### 四、`merge` 的卡迁移：改用原生驱动

mongoose 会按 schema 把 `_id` **转成 ObjectId**。正式库的 `_id` 确实是 ObjectId，

## 「一键上架」落进主程序：第七步 · 整页重写（V1.2.64）

### 顶层结构：待上架库底下的两块

原型只有一个「待上架库」页签。真页面保留 **本地库 / 云端库 / 待上架库** 三个 ——

标记接口只在这两屏上有按钮），撤掉就没地方标记了。

「待上架库」底下的两块，跟原型一致：

- **待上架包** —— 按 `packCode`（编号前缀，如 `QCAC`）分组，一组一张包卡片；
- **已上架包** —— 从 `listingbatches` 里 `state:'listed'` 的批次反向读 `ListingQueue`

包卡片上有：进度条（成功数 / 总数）、流程 A/B/C 彩色 chip、状态字（`剩 N 行` / `可完成` /

### 新增后端：`POST /listings/queues/:batchId/item/:index/mark-listed`

它是给「流程跑红了、但人已经在店里手工上架了」这种行用的 —— 没有它，那行会一直红到归档为止。
守卫复用取条目那套（归档过 / 撤回过的批次 409、行不存在或跨用户 404），另外：

- **拦执行中**（409）：跑着的时候不允许从底下改结论，模拟器一回来就会覆盖掉；

1. **保留本地库 / 云端库两个页签** —— 它们是「标成待上架」的唯一入口，原型没有这一步的入口；

## 「一键上架」落进主程序：第六步 · 执行链路加固（V1.2.63）

三步都只动后端和执行器，页面上只有一个按钮改了。

### 急停原本是个摆设：执行期间事件循环被占死

VM 执行器（`listing-agent-vm/executor.js`）整趟流程是**同步**的 —— `screen.js` 的 `sleep` 是忙等
（`while (Date.now() < end) {}`），步骤间延迟那句连 `await` 都没有；`dumpUI` / `screenshot`
又都是 `execSync`。Node 是单线程，所以**跑批期间服务器一个请求都处理不了**：
终止按钮发出去的那个 `POST /execute/stop` 排在队尾，等它被读到，整批早就跑完了。

> 这条比「两个批次互相踩中止旗子」更根本 —— 光把旗子按批次隔离，急停照样按不动。

改动：

- 步骤间延迟改成 `await sc.sleepAsync(delay)`，`wait` 步骤同样；
  `sleepAsync` 补进 `screen.js` 的导出（原先定义了却没导出）。
- 于是每步之间让出一次事件循环，终止请求有机会被处理。
- **残留局限**：单个 `execSync`（`dumpUI` / `screenshot`）自身仍会阻塞几百毫秒到一秒，
  所以按下停止是「当前这一步做完才停」——这跟按钮上写的文案是一致的。

### 中止旗子按批次隔离

原先是一条模块级的 `let _aborted = false`，毛病有两个：

1. **谁点停谁全停**：手动面板点一下终止，正在跑的那一批也跟着停；
2. 更阴的：`executeSteps` 开头会 `resetAbort()`，所以**后开始的那次执行会把前一次的中止旗子清掉** ——
   前一批永远停不下来。

现在旗子是一张 `Set`，键是运行标识：上架批次传 `batchId`，手动面板不传（落在空串那一槽，各停各的）。
`POST /execute/stop` 收 `{batchId}`，不带就停空串那一槽；前端急停按钮带上 `currentBatchId`
（没有批次号时干脆不发，免得「不知道在停什么」还打一枪）。
VM 和 PC 两个执行器是**两个独立模块、各有一张表**，`auto-listing.vue` 也是按模式分别打两个端点的。

### 成功判定：改成读流程自己声明的 `successCode`

原先写的是 `status.includes('成功99')` / `status.startsWith('报错')` —— 拿**自然语言的文案**当判据。
流程文案一改（比如把「输入成功99」写成「上架成功」），就会**静默**把整批标成失败，看日志都看不出来。

现在流程 JSON 顶层带一个 `successCode`（流程A / 流程B 都填了 `"输入成功99"`），
跑完吐出来的状态**等于**它才算成功，其余一律算失败：

- 「加一条新的报错码」不用改后端；
- 判据变严了：`输入成功99（已复核）` 这种「包含但不等于」的从前会被当成成功，现在算失败；
- 一个字都没吐（中止、或流程里压根没有设置状态的步骤）也判失败 —— **宁可错杀，不许放过**；
- 没带 `successCode` 的老流程退回按 `成功99` 判，并**打一行日志**提醒（每个流程只提醒一次）。

> 顺带说明 VM 侧的 `流程C-更新.json`：它是个 29 步的半成品，**一条「运行状态(输出)」都没有**，
> 而且 `auto-execute-vm.js` 从来不加载它（VM 的 C 走 B）。**这次没有删它**（可能是你正在做的活），
> 但按新判据，万一被拿去跑，结果是**判失败**而不是静默成功 —— 不会再骗人。要不要删/要不要补全，你说了算。

### 上架价格 `listingPrice`：独立字段，不是 `outputPrice`

| 字段 | 是什么 | 谁写 |
|---|---|---|
| `outputJhj` / 集换价(输出) | 集换价，打底用的参照 | 模拟器 |
| `outputPrice` / 价格(输出) | 第三个参考数，**只读** | 模拟器 |
| **`listingPrice`** | **要挂到店里去的价** | 自动跑完打底 ＋ 人手工改 |

跑完**只在这一行还没有价的时候**，拿集换价打底。判断「有没有价」放在**查询条件**里交给数据库做
（`$or: [{listingPrice:''}, {listingPrice:null}, {listingPrice:{$exists:false}}]`），
不是先读出来在 JS 里比 —— 用户完全可能在这一张正跑着的时候手填了价，先读后写会把他刚填的冲掉。
老队列行里压根没这个字段，所以 `$exists:false` 也算「空」。

> 口径提醒：既然是「仅当为空」，**打底是一次性的** —— 打上之后就冻结在第一次那个集换价上，
> 后来集换价变了也不会自动跟。要改成「用户没碰过就跟着刷新」，得再加一个「这价是人改的吗」的标记，
> 这次没做（不在本步口径内）。

手工改价：`PUT /listings/queues/:batchId/item/:index/price` `{price}`。
只收数字（最多两位小数），传空串＝清掉（下次跑完会被集换价重新打底）。
`¥` / `元` / `,` 这些一律 400 —— 价格是要喂给上架流程的，混进非数字字符到那儿才炸，不如在入口拦住。
**执行中不拦**：跑着的时候人可以改价，上面那个「空才填」的过滤条件在数据库那层就把它保护住了。

## 「一键上架」落进主程序：第四步 · 删除键 / 单卡重跑 / 执行互斥（V1.2.61）

### 删除键：删的是**实体卡**

详情抽屉里每一份一份地删，或者整行删。语义是「这份卡不跟着这批上架了」——
所以卡是从库里**真删掉**的，不是从这一行上摘下来留着：摘下来它就变成没主的孤儿卡了。

| 接口 | 做什么 |
|---|---|
| `POST /listings/queues/:batchId/item/:index/remove` `{serials:[…]}` | 逐份删 |
| `POST /listings/queues/:batchId/item/:index/remove-all` | 整行删 |

删完 `serialList` 摘掉那几份、`addQty` 跟着减（**最少留 1**）、`totalQty = existQty + addQty` 重算；
**摘空则整行删掉**（留着的话它就是个永远跑不动的 `pending`，会把「确认完成」卡死），
再对动过的库跑一次 `syncStockCode` 修卡数。

两处刻意没做：

- **不压实卡位号**。压实是「确认完成」那一步统一做的（`batches.js`）。中间每删一张就重排一次，
  等于把 `OrderPick.position` 认的那把钥匙反复挪动。
- **不碰 `listed` / `reverted` 的批次**。已归档的那批不许再改条目（要改先撤回），打 409。

**先落快照再动手**：`saveSnapshot` 写不进去直接 500，一个字都不删 ——
删卡不可逆，那份逐张记全字段（`_id` 存成**字符串**，JSON 存不下 ObjectId 的类型）的快照是唯一的记录。

> 踩到的坑：审计文件名光靠 `makeStamp()` 是不够的。它只到秒，而「删一份」会被连点好几次，
> 同一秒里同一行删 5 次的话 `openAudit` 的 `writeFileSync` 会把前 4 份**悄悄覆盖**掉，
> 只留最后一次。所以文件名末尾补了 `Date.now()`（和 V1.2.60 归档快照改名同一个路数）。

### 单卡重跑

`POST /listings/queues/:batchId/item/:index/rerun` 只把这一行置回 `pending`，**不碰模拟器** ——
真正跑还是下次点「一键上架」的时候。它同时是**清掉僵尸行**的唯一出口（见下）。

### 执行互斥：同一批不能跑两遍

新增 `running` 态（`ListingQueue.itemStatus`）。双击「一键上架」、或者局域网里两台设备同时点，
不能让同一批在模拟器上把 ADB 动作做两遍。两道保险：

1. **进程内的锁**（`services/listingRunLock.js`，和订单那边 `passingLocks` 同一路数）→ 409「请勿重复点击」；
2. **库里的痕迹**：上一次跑到一半进程没了的话，会留下 `running` 的行 → 409 并点名有几张。
   这种行**不会自己变回 `pending`**（宁可停在那儿让人看见），得人去点「重跑」。

跑完（或中途炸了）在 `finally` 里把本批还没拿到结论的行放回 `pending` ——
不这么做的话它会永远停在 `running`，下次进来就被上面第 2 道挡在门外，谁也跑不了。

**聚合口径跟着改**：`running` 必须一起算进「还没跑完」——
否则「正在跑」的批次也满足 `pending=0 && failed=0`，会提前出现在「已上架」里（跑着跑着就被当成跑完了）。

### 顺手清掉的

- 删了死接口 `PUT /listings/queues/:batchId/item/:index`（全仓无调用者）。
- 页面刷新后从队列还原时，`inventory` 现在按 `serialList` 填回来 —— 不填的话一刷新这份列表就是空的，
  「逐份删除」也就无从谈起。

## 「一键上架」落进主程序：第三步 · 撤回照存档还原（V1.2.60）

**撤回不再是一把钝器。** 老写法只有一句：

```js
StockCode.updateMany({ listingBatchId: batchId }, { $set: { listingBatchId: null, status: 'pending' } })
```

两处毛病：① **不看原来是什么状态** —— `in_use`（本地库里正用着）也好 `full`（满了）也好，
一律写成 `pending`，原状态就丢了；② 归档时不清 `listingBatchId`，于是**已上架的批次也匹配得上**，
撤回会把店里可能正在卖的卡打回 `pending`。

现在 `POST /v1/api/listings/queues/:batchId/revert` 改成**读 `listingbatches.snapshot` 逐库原样还回去**：
`status` / `libraryType` / `assignedTo` / `currentCards` / `listingBatchId` 五个字段照解析前那一刻。
`currentCards` 用**现数**（`Card.countDocuments`）而不是照抄快照值 —— 万一这批中间删过卡，
现数才是真的（现阶段两种走法都不删卡，所以两者相等）。

**已归档的那批多还两样。** 归档动过每张卡的两个字段 —— 卡位号（压实重排）、原图链接（清空）。
所以归档那份快照从 `serials-before-<批次号>.json` 升级成 **`cards-before-<批次号>.json`，逐张记 `serial` 和 `origImg`**；
撤回时按 `_id` 逐张 `$set` 回去。快照读不到就**直接 500 打回，不盲撤** ——
卡位号和原图回不去的事，不能装作撤成了。档案里记着归档那一次的 `auditStamp`，就是拿它找回这份档。

**两条前置拦截**（都不写库）：

| 情况 | 返回 |
|---|---|
| 这个批次没有档案（V1.2.58 之前的老批次，没快照就无从还原） | 404 |
| 库上还挂着没拣完的拣货单（`OrderPick.pickStatus != picked`） | 409 —— 还原要写卡位号，而卡位号正是拣货单认的那把钥匙 |

**页面**：工具栏那枚「撤回」和已上架库里每行的「撤回」都先弹确认框，文案写清批次号、涉及哪些库、
会还原什么；后端打回时**弹框显示原因并且不清视图** —— 没撤成就别装作撤成了。
已上架库这屏现在**先读批次档案**（`GET /listings/batches?state=listed`），
读不到才退回老路子（`GET /listings/queues/completed`）；只有带档案的行才显示「撤回」键。

审计：`Storage/carduniques-audit/` 一条 `listing-revert`，分 `begin` / `stockcodes-restored` /
`cards-restored` / `queue-cleared` / `done` 五步落盘。**档案不删**，`state: reverted` 留着当「这批被撤过」的痕迹。

## 「一键上架」落进主程序：第二步 · 确认完成（V1.2.59）

**归档从「自动」改成「人工点」。** 原先归档写在 `auto-execute.js` / `auto-execute-vm.js` 里，
判据是 `okCount === totalCount` —— 左边是**本次执行**成功的张数，右边是**整批**张数，两个口径不同。
于是只要失败过一次（哪怕后来重跑全绿），这个等式永远不成立，**门永远开不了**；
反过来，页面的「已上架库」读的是 `GET /listings/queues/completed`（判据是队列跑绿没跑绿），
跟那道门毫无关系 —— 就出现了「页面说已上架、实体卡还 `locked`」的静默不一致。

现在两道都拆了：**归档只有一个入口** ——

```
POST /v1/api/listings/batches/:batchId/complete
```

页面上是工具栏里那枚绿色的「确认完成」。它依次做四件事：

1. **库归档** —— `status: archived`、`libraryType` 清空、**`listingBatchId` 一并清成 null**
   （不清就是颗雷：这批一旦在「已上架库」里被撤回，会把店里可能正在卖的卡打回 `pending`）
2. **清原图链接** —— 该批库里的卡 `origImg` 清空（原图文件留着，走「原图缓存管理」）
3. **压实卡位** —— 每个库的卡位号重排成 `0001,0002…` 连续，然后同步 `currentCards`
4. **档案收尾** —— `state: listed`、`completedAt`

**先落盘再动手**：动手前先写一份审计（`Storage/carduniques-audit/`）和一份卡位号快照
（`Storage/carduniques-backup/<戳>/serials-before-<批次号>.json`）。
快照文件名**带批次号** —— `makeStamp()` 只到秒，同一秒归档两批的话，固定名会被后一批悄悄覆盖。
（V1.2.60 起这份档改名 `cards-before-<批次号>.json` 并多记一个 `origImg`，见下一节。）

**三道前置拦截**（都不写库，直接打回）：

| 情况 | 返回 |
|---|---|
| 这批还有 `itemStatus: pending` 的没跑完 | 400「还剩 N 张没跑完」 |
| 库上还挂着没拣完的拣货单（`OrderPick.pickStatus != picked`） | 409 —— 归档要重排卡位号，而卡位号正是拣货单认的那把钥匙 |
| 已经确认完成过 / 已经撤回过了 | 400 |

`itemStatus: failed` 的**不拦** —— 那是留给人看的，删不删由人决定。

**顺带搬家**：`compactLibrarySerials` / `syncStockCode` 原先长在 `routes/orders/index.js` 里、没导出，
现在挪到 `services/librarySerials.js` 供两边共用（`orders` 改成 require，**行为一字未改**）。

> ⚠️ 一个副作用要知道：`listingBatchId` 一清，`libraries/index.js:171/374` 那两处 423 拦截
> （「该库已被上架批次锁定，请先撤回解析」）就**不再拦已归档的库**了。那句提示对已归档的库本来也不成立
> （都归档了还「撤回解析」什么），所以口径是顺的；但确实意味着已归档的库现在能被 `DELETE /libraries/:code` 删掉。

## 「一键上架」落进主程序：第一步（V1.2.58）

原型（`Client\mock\listing-board.html`）谈定之后，把它往真程序里搬。这一步**只加东西，
不改任何现有判据**，是后面几步（人工确认完成 / 撤回照存档还原 / 删除键）的地基。

**新增集合 `listingbatches`（批次档案）**，一次「开始解析」= 一批：

- `snapshot` —— 解析**之前**把那几个库的原样（`status` / `libraryType` / `assignedTo` /
  `currentCards` / `listingBatchId`）抄一份下来。没有它，撤回只能一律写回 `pending`，
  库原来在本地库里用着（`in_use`）还是满了（`full`）就丢了。
- `state` —— `parsing` / `listed` / `reverted`。归档从此由人工点，不再看队列跑绿没跑绿。
- `stats` —— `libCount` / `packCount` / `rowCount` / `cardCount`，列表页文案直接用。

**`listingqueues` 多两个字段**：`packCode`（包 = 编号前缀，`QCAC-JP001` → `QCAC`，
后端自己从 `code` 算，前端给不给都不影响）和 `serialList`（这一行涉及的实体卡位号，
详情逐份列出和逐份删除都靠它）。

**建档顺序照 `cardAudit` 的老规矩：先把存档落到盘上，再动手改数据。**
`POST /v1/api/listings/queues` 现在是「生成批次号 → 读库现状 → 写 `listingbatches` →
写 `listingqueues` → 最后才锁 `StockCode`」。任何一步炸了，前面没动过的库原样不动
（单机 MongoDB 没有副本集，跨集合写入没有回滚，所以顺序就是保险）。

**这一步不写 `stockcodes` 的状态流转**（只读一遍存快照）—— 锁库那一下还是老逻辑，一字未改。

## Server\Storage\ 不会进 git

`Server\Storage\`（软删的图、改编号的审计 JSON 和图片备份）是运行时数据，已在 `.gitignore` 里整片挡掉。

> 留意：`.gitignore` 里早先那批 `Storage\mongo\` / `Storage\backup\` 规则是**带中间斜杠的**，
> 只会匹配仓库根的 `<根>\Storage\`，管不到 `Server\Storage\`。
> 而关服务时的 `autoGitSave` 走的是 `git add -A` —— 不挡的话每次关服务都会把几十 MB 的图片备份提交进仓库。
> 所以这里用的是 `Server/Storage/` 整目录，而不是逐个列子目录。

## 改了前端要重新编译

后端托管的是 **`Client\dist\build\h5\`** 这份编译产物，不是 `Client\src\`。
**改了 `Client\src` 之后必须重建**，否则浏览器里跑的还是旧代码：

```bash
cd Client
npm run build:h5
```

（只在改前端时才需要。只改后端 `Server\` 的话，重启服务即可。）
