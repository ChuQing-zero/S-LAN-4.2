# 拍照往返耗时实测（2026-11-09）

测量对象：`GET http://127.0.0.1:6001/vision/photo`
含义：从电脑发出请求，到拿回可送 AI 的图片（dataURL），全过程耗时。
测量条件：无线 adb（192.168.1.123:5555）、相机在前台、补光灯常亮、拍照期间投屏线程已暂停。

---

## 一、总耗时

| 次数 | 总耗时 | 结果 | 图片大小 |
|---|---|---|---|
| 第 1 次 | 8626 ms | 成功 | 109 KB |
| 第 2 次 | 9243 ms | 成功 | 132 KB |
| 第 3 次 | 7964 ms | 成功 | 129 KB |
| **平均** | **8611 ms** | 3/3 | — |

波动范围 7964 ~ 9243 ms，约 ±700 ms。

---

## 二、分段耗时

| 阶段 | 平均 | 三次实测 | 说明 |
|---|---|---|---|
| 拉起相机 | **302 ms** | 261 / 420 / 224 | 查前台应用，不在前台才拉起 |
| 对焦 | **2280 ms** | 2029 / 2935 / 1875 | adb 点屏幕 + 等 600 ms |
| 点快门 | **1865 ms** | 1915 / 1744 / 1936 | 一条 adb 点击命令 |
| 等照片落盘 | **1771 ms** | 2760 / 1371 / 1183 | 反复问相册"生成新文件了吗" |
| adb 取回 | **2088 ms** | 1459 / 2568 / 2236 | 传 3~5 MB 全分辨率原图 |
| 缩图编码 | **263 ms** | 130 / 181 / 478 | 缩到宽 720、JPEG q82 |
| 合计 | **约 8570 ms** | — | 与总耗时基本吻合 |

---

## 三、单条 adb 命令的基准开销（无线）

| 命令 | 耗时 |
|---|---|
| `adb shell true`（空命令，纯往返） | 375 ms |
| `adb shell dumpsys window` | 311 ms |
| `adb shell ls 相册` | 356 ms |
| `adb shell input tap` | 577 ms |
| `adb shell input keyevent 27` | 781 ms |
| 两条 tap 合并成一条 shell | 854 ms |

拍照过程中同样的 `input tap` 要 1.8 秒（基准 577 ms），差值来自：相机前台占 CPU、相册写入磁盘、以及残余的 adb 请求排队。

---

## 四、结论

1. 一张照片的往返稳定在 **8.6 秒左右**，不是偶发慢。
2. 三段最贵且几乎等长：**对焦 2.3 s、点快门 1.9 s、取回 2.1 s**，再加等落盘 1.8 s。
3. 这四段里只有"等落盘"是手机写盘，**其余三段都是 adb 命令往返本身的开销**。
4. 已做的两项优化：拍照期间暂停投屏线程、第二次停延时改 0。相比最初 7.9 s 的单次测量，本次 3 次平均 8.6 s，说明**继续靠改软件参数能压的空间不大了**。

---

## 五、还能压缩的选项

| 做法 | 预计省 | 风险 |
|---|---|---|
| 关掉拍照前对焦 `FOCUS_TAP=false` | 约 2.3 s | 卡面可能虚焦，需实测 AI 是否仍能正确分类 |
| 对焦等待 600 → 300 ms | 0.3 s | 基本无感 |
| 等落盘轮询间隔 0.2 → 0.4 s | 0.2~0.3 s | 最坏多等 0.2 s |
| 快门改 `keyevent 27` | **不省反慢**（781 vs 577 ms） | 不建议 |

**若要压到 5 秒以内，只靠软件参数调不动，需要换思路**（例如：手机端装一个常驻采集 App、用局域网 HTTP 直接传图，绕开 adb）。
