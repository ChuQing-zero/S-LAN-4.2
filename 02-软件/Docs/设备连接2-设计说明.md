## 一、页面定位

`设备调试` 是**操作页**（点按钮让机器动）；
`设备连接2` 是**链路管理页**（管怎么连、连没连上、连的是谁、出问题怎么查）。

两页分工：

| 页面 | 职责 |
|---|---|
| 设备调试 | 下发指令、看动作反馈、调参数 |
| **设备连接2** | 有线/无线链路切换、连接参数、固件信息、指令映射表、连接日志 |

## 四、要不要做数据库？

### 结论：**建议做，但只做轻量的两张表**

理由（答辩可讲）：

1. **操作可追溯** —— 谁在什么时候通过哪条链路发了什么指令、结果如何，出问题能回查
2. **链路质量统计** —— 累计连接次数、断线次数、平均在线时长，可以画成论文里的图
3. **成本很低** —— MongoDB 已经在跑（28018），加两个集合即可，不增加部署负担

### 建议表结构

**表1：`device_link_log`（链路事件）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | Date | 时间 |
| `mode` | String | auto / serial / wifi |
| `event` | String | connect / disconnect / switch / error |
| `peer` | String | `192.168.1.100:8080` 或 `COM7` |
| `detail` | String | 错误原因等 |

**表2：`device_cmd_log`（指令记录）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | Date | 时间 |
| `cmd` | String | 下发的指令原文 |
| `reply` | String | 上行首行反馈 |
| `ok` | Boolean | 是否成功 |
| `link` | String | serial / wifi |

**可选表3：`device_test_record`（联调测试记录）** —— 给论文表 5-6 用
| 字段 | 说明 |
|---|---|
| `ts` | 时间 |
| `cardId` | 卡号 |
| `identType` | QR / NFC |
| `exit` | 落到哪个出口 |
| `elapsedMs` | 耗时 |
| `ok` | 是否成功 |

> **表3 是给整机联调成功率统计用的**，比手工记 Excel 强，而且能直接出图。

### 如果不想做

只做**内存里最近 50 条日志**（现在就是），重启即清空，不落库。**够用，但答辩少一个亮点。**
